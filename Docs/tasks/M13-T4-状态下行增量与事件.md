## 2. 目标（一句话）

> step 下行升级为规格中的 **StateDelta**（基于版本 basedOn + 新版本 version + 变化 changes + 事件 events），并提供**客户端状态同步器**：按版本裁决应用增量（重复丢弃 / 空洞不猜合并 / 拒绝步不动状态），**客户端应用增量后视图与权威状态一致**（Docs/02 AC）。

## 3. 范围（做什么）

- **step 消息补 `basedOn` 字段**：增量所基于的权威版本 = **结算前的 StateVersion**（接受命令时 = version − 1；被拒时状态未变，basedOn == version）。满足 §5.2 规则 2"每条 delta 必须可独立重放：包含基于版本 + 目标版本"。
- **快照补 `version` 字段**：hello 快照携带产生它的权威 StateVersion（§5.2 `MatchSnapshot.StateVersion` 的落地）。理由：客户端增量基线必须来自快照——双座位下后加入端点的快照版本可能 >0，没有它首个增量必被判空洞。快照**回退机制**（SnapshotRequest）仍是 T5。
- **新文件 `ClientStateSync`**（`Card.Application.Match`，纯 BCL 客户端状态同步器）：
  - `ApplySnapshot(JsonValue)`：载入快照（state + version 基线）；
  - `ApplyStep(JsonValue)`：按 §5.2 规则 1 裁决——`version ≤ 本地` → 重复包丢弃（不执行不回退）；`basedOn ≠ 本地` → 版本空洞**不猜合并**（状态零变更，等待补齐）；`basedOn == 本地` 且接受 → 经 `StateChangeApplier` 应用 changes、推进本地版本、透传事件；`accepted=false` → 拒绝步不动状态与版本，拒绝原因透传表现层；
  - 暴露 `LocalVersion` / `State` / 应用结果（状态 + 拒绝原因 + 事件原文）供表现层消费。
- **T2/T3 登记项裁决**：CommandAccepted/CommandRejected 与 StateDelta **维持单一 step 帧型广播**——step 已含 accepted/error/seq/changes/events 全部语义（等价于 §9.1 三类消息合一带内承载）；拆分专用帧型 + 回执单播属于带宽优化，本机房主模式验证阶段不做（登记设计决策 1）。

## 4. 明确不做（防止范围蔓延）

- **SnapshotRequest / 快照自动回退** —— T5（本任务只做"快照带版本 + 空洞检测"，收到 Gap 时仅报告不请求）；
- **真实视野裁剪** —— T6（增量仍按权威全量 diff 下发，经既有座位投影快照路径）；
- **掉线重连** —— T7；异常注入矩阵（乱序/超长/非法字段全谱系）—— T9；
- **事件反序列化为 GameEvent 对象**：同步器透传事件 JSON 原文，表现层需要强类型时再补（EventSerializer.ReadEvent 已存在，随时可用）；
- 客户端插值 / 预测与和解（§5.5 / §6）；专用 Accepted/Rejected 帧型与单播（见范围末条裁决）。

## 5. 接口约定

```csharp
// step（StateDelta 帧载荷）：新增 basedOn，其余字段不变（协议"只加不删"）
// { kind:"step", version, basedOn, seq(可选), accepted, error, detail, finished, changes[], events[] }
// snapshot：{ kind:"snapshot", version, state }   ← 新增 version

// MatchHostProtocol.cs（扩展签名，internal）
public static JsonValue WriteSnapshot(MatchState state, ulong version);
public static JsonValue WriteStep(ulong version, ulong basedOn, int? seq, bool accepted,
    CommandError error, string detail, bool finished,
    IReadOnlyList<StateChange> changes, IReadOnlyList<GameEvent> events);

// ClientStateSync.cs（新文件，Card.Application.Match，public——表现层/客户端复用）
public enum StepApplyStatus { Applied, Rejected, DuplicateDiscarded, VersionGap }
public sealed class StepOutcome
{
    public StepApplyStatus Status { get; }
    public bool Accepted { get; }
    public int? Seq { get; }
    public CommandError Error { get; }            // 拒绝步有效
    public string Detail { get; }
    public IReadOnlyList<JsonValue> Events { get; } // 事件 JSON 原文（透传表现层）
}
public sealed class ClientStateSync
{
    public ulong LocalVersion { get; }
    public MatchState State { get; }
    public void ApplySnapshot(JsonValue snapshotJson);   // 载入基线（可重复调用 = 重置）
    public StepOutcome ApplyStep(JsonValue stepJson);    // 版本裁决 → StateChangeApplier.Apply
}

// MatchHost：SubmitAndBroadcast 捕获结算前版本作 basedOn；Reject 路径 basedOn = 当前版本；
// ProcessHello 快照携带 _stateVersion。
```

**设计决策登记**（待确认问题 → 已裁决）：
1. **Accepted/Rejected/StateDelta 维持单一 step 帧型广播**（T2/T3 登记项裁决）：step 已含 accepted/error/seq/changes/events 全部语义，等价于 Docs/05 §9.1 三类消息合一带内承载；拆分专用帧型 + 回执单播是带宽优化，本机房主模式验证阶段不做（M14 复盘时再评估）。
2. **basedOn 语义 = 结算前权威版本**：接受命令时 = version − 1（diff 以 before 副本为基准），拒绝时 = version（状态未变）；满足 §5.2 规则 2"每条 delta 可独立重放"。
3. **快照携带 version 属 T4 而非 T5**：客户端增量基线必须来自快照——双座位下后 hello 端点的快照版本可能 >0，没有它首个增量必判空洞（AC-8 场景）；T5 只做 SnapshotRequest 与自动回退机制。
4. **客户端同步器放 `Card.Application.Match`**：纯状态逻辑无网络依赖，与 MatchHost/StateChangeApplier 同层共享（未来 DedicatedHost 客户端同样复用）；Card.Network 只做帧化（铁律 12 网络代码边界不变）。
