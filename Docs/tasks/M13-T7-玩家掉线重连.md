## 2. 目标（一句话）

> 对局进行中座位 1 掉线后，**同一座位可通过新连接重连并恢复**：握手后发送 `RequestSnapshot`（T5 移交的 TCP 帧化接线），主机校验对局仍在进行后单播**按座位裁剪**的当前快照，客户端重置基线后增量继续——重连窗口内可恢复，超时判掉线（M12-T7 既有机制）后重连同样可用。

## 3. 范围（做什么）

- **`NetworkMessageType.RequestSnapshot = 23`**（C→S，载荷 `{ "version": N }`，与内核 `snapshot_request` kind 对齐）——T5 移交项：`ClientStateSync.BuildSnapshotRequest` 的产物经 `MessageCodec.Frame` 走真实传输。
- **`PeerSession` 新增 RequestSnapshot 分支**：握手（Hello→HelloAck）后有效 → 经桥接器向权威上行注入 `snapshot_request`；未握手收到 → 丢弃记日志（T9 完善注入矩阵）。重连流程 = 新 TCP 连接 + Hello + RequestSnapshot，**不再发 Ready/MatchStart**（对局已开始）。
- **`PeerHost.AcceptPeer` 重连接管**：Accept 新连接前把旧座位 1 会话的桥接端点从权威 Detach（旧端点不再广播），随后按原流程挂新端点建新会话。
- **`MatchHost.Detach(endpoint)`**：从广播列表、座位映射与 AttachedSeats 移除端点——防止断线端点无限积压下行（内存泄漏）与幂等回执错位。
- **`HostBridge` 上行泛化**：`TryValidateUplink` 接受 `kind == "snapshot_request"`（与 command 同等校验：合法 JSON + 已知 kind）；`ForwardCommand` 更名 `ForwardUplink`。
- **恢复链路复用 M13-T5**：快照 `ApplySnapshot` 重置基线 → 后续 step 增量继续；快照与增量统一经 `PlayerViewProjector` 裁剪（铁律 12：重连不能成为绕过裁剪的通道）。

## 4. 明确不做（防止范围蔓延）

- **`ReconnectRequest` 独立帧类型**（§9.1 表含"对局 Id + 本地版本号"）——阶段二单一对局 + 固定座位 1，重连请求在协议上等价于"新连接 + 请求快照"，对局 Id 无处校验、无从歧义；按 §15.2 范围收缩原则以 `RequestSnapshot` 承担（设计决策 2 登记，阶段三引入多对局时再改文档补类型）；
- **MatchEnd 帧（掉线判负 / 结束原因通知）**——M13-T8 异常与终态；
- **掉线/重连的 UI 提示**——M14-T6 异常体验打磨；
- **重连窗口 30 s 与"离线判负"计时器**（§8.2）——判负属 T8；本任务的"超时判掉线" = M12-T7 既有 `PeerSession.TimedOut`（60 tick），且验证超时后重连仍可用；
- **会话令牌 / 身份校验强化**——阶段三（反作弊）；
- **双方同时掉线作废、主动投降**——T8。

**设计决策登记**：
1. **RequestSnapshot 承担重连请求**（§9.1 ReconnectRequest 简化）：阶段二单一对局 + 固定座位 1，重连在协议上等价于"新连接 + Hello + RequestSnapshot"，对局 Id 无处校验也无歧义；独立 ReconnectRequest 帧类型与对局 Id 校验留待阶段三引入多对局时随文档一并补。
2. **重连激活免二次 Ready**：新会话不重放 Ready 流程（对局已在进行），由 RequestSnapshot 处理即置对局激活——Command 门控、心跳门控（`_handshook` 后才发 Ping）均按此语义放行。
3. **旧端点 Detach 而非复用**：断线端点的桥接回环对从权威摘除、新连接建新 pair——避免向死端点持续积压下行（内存泄漏）与幂等回执错位；旧 PeerSession / HostBridge 对象随之废弃。
4. **MatchHost 瘦身**：`TryReadSeq` / `ExtractPayloadJson` 为纯信封解析，移入 MatchHostProtocol（与 ReadKind / TryReadCommand 同类），MatchHost 299 → 283 行，为 Detach 腾出行数空间。
