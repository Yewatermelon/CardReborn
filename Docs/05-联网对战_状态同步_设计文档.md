# 05 联网对战（状态同步）设计文档

> 版本：**3.0** ｜ 状态：设计基线（Design Baseline）
> 上游依据：[01-开发需求文档](./01-开发需求文档.md) FR-13 / FR-14、[00-现状解构与架构再设计](./00-现状解构与架构再设计.md) ADR-11～14
> 本文定义**联网 PVP 的网络结构**：服务端权威 + 状态同步（Server-Authoritative State Replication）。
>
> **变更说明**：
> 2.0 版把网络结构从帧同步（锁步）改为状态同步，见第 14 节；
> **3.0 版把范围收敛为"在单台 PC 上用监听服务器（房主模式）验证双人联网"**，见第 15 节。

## 1. 目标与范围

| 项 | 内容 |
| --- | --- |
| 目标 | **在单台 PC 上验证双人联网对战**（监听服务器模式）；网络结构为**权威状态同步**；PVE 保持为基础功能且完全不受影响 |
| 权威方 | **房主客户端**。房主进程内运行唯一的规则实例，另一个客户端（或同一台 PC 上的第二个实例）连接它 |
| 拓扑 | **只做房主模式（`PeerHost`）+ 本地模式（`LocalHost`）**；专用服务器（`DedicatedHost`）**推迟到未来，本阶段不实现** |
| 连接范围 | **本机回环（127.0.0.1）为主**，可选局域网（同一路由器下两台设备）；不做公网对战 |
| 同步对象 | 权威宿主产出的**状态快照与增量**（玩家可见子集）+ 事件通知 |
| 上行内容 | 玩家意图（`GameCommand`），例如"出第 3 张手牌指向对方随从 2" |
| 权威 tick | 默认 **10 Hz**（可配置），回合制游戏对 tick 精度不敏感 |
| 客户端表现 | 状态驱动渲染 + 插值；只需"表现先行"，**预测与和解在本阶段可省略**（回环延迟接近 0） |
| 反作弊 | **本阶段不承诺任何反作弊**。房主即对手，可看到手牌、可改状态；本阶段目标只是功能与流程验证 |
| 阶段 | 阶段一（M0–M10）只做**接口与结构预留**；阶段二（M11–M14）实现**本机房主模式验证** |
| 不包含 | 专用服务器、匹配/排队服务、NAT 穿透、中继（TURN）、公网对战、排位、观战、聊天、赛季、账号体系 |

### 1.1 一句话概括架构

> **规则只在权威宿主上跑一次；客户端把"我想做什么"送上去，把"现在是什么样"收下来并渲染。**

### 1.2 与旧方案（帧同步）的关系

| 项 | 帧同步（已放弃） | 状态同步（本方案） |
| --- | --- | --- |
| 谁跑规则 | 每个客户端各跑一份 | **只有权威宿主跑**（本阶段 = 房主客户端） |
| 网络传什么 | 输入帧 | 权威宿主产出的状态/事件 |
| 客户端能否看到全局状态 | 能（隐藏信息靠遮蔽，可被读取） | 非房主一方**不能**（收到的是裁剪后的数据） |
| 逻辑层是否必须零浮点 | 是（硬要求） | **否** |
| 客户端作弊难度 | 低 | 非房主方：中；房主方：无防护（本阶段不处理） |

## 2. 为什么状态同步更适合本项目

### 2.1 决策依据

| # | 理由 | 说明 |
| --- | --- | --- |
| 1 | **隐藏信息天然安全** | 手牌、牌库顺序是卡牌游戏的核心信息。状态同步下服务器**只下发该玩家有权看到的内容**，对手手牌只下发"数量"。帧同步做不到这一点（每个客户端都要算出全局状态）。 |
| 2 | **撤销高成本约束** | 帧同步要求逻辑层零浮点、零系统时间、固定遍历顺序、跨平台逐位一致。状态同步没有这个要求，规则层可以用常规写法，**开发成本与返工风险显著下降**。 |
| 3 | **结构上更贴合卡牌游戏** | 客户端不跑规则，命令必须过权威校验；非房主一方改内存只影响自己的显示（本阶段不做反作弊，但这个结构为将来留了路）。 |
| 4 | **带宽对卡牌游戏完全够用** | 回合制的状态变化是**事件驱动**的，只有状态真变了才发包。一局下行总量通常在几十 KB 量级。 |
| 5 | **回合制对延迟不敏感** | 一次操作 200–300 ms 生效对卡牌游戏完全可接受，不需要回滚式同步。 |
| 6 | **规则代码只有一处实现** | `Card.Domain` 零 Unity 依赖；房主进程、普通客户端、将来的专用服务器引用的是同一份源码。 |

### 2.2 代价（必须正视）

1. **必须有一个"权威运行时的宿主"**。本阶段该宿主就是**房主客户端进程**（见 2.4），因此不需要部署任何服务器。
2. **权威宿主成为关键路径**。房主进程退出 = 该局结束（PVE 不受影响，这是阶段一就要保证的隔离）。
3. **需要设计状态序列化与增量**。帧同步不需要（只传输入），状态同步必须把状态结构设计成可序列化、可裁剪、可增量的形式。
4. **房主模式没有反作弊**。房主即对手，能看到手牌、能改状态。本阶段目标是验证功能与流程，**不用于公开对战**。
5. **本机验证与真实公网存在差距**（见第 12 节 Q-8）：回环几乎无延迟丢包，真实网络的抖动、NAT、中继问题在本阶段不会被暴露。

### 2.4 部署拓扑：权威运行时放在哪里（重要）

这里要纠正一个常见误解：**帧同步并不是"不需要服务器"。** 两者的真实区别在于"服务器上要不要跑规则"：

| 需要什么 | 帧同步（锁步） | 状态同步 |
| --- | --- | --- |
| 权威逻辑服务器（跑完整规则、做校验） | ❌ 不需要 | ✅ 需要（可以放专用进程，也可以放房主客户端） |
| 玩家之间的可达性（NAT 穿透 / 中继） | ✅ 需要 | ✅ 需要 |
| 大厅 / 房间 / 匹配 / 信令 | ✅ 需要 | ✅ 需要 |
| 帧（或状态）节奏的协调者 | ✅ 需要（房主或专用调度） | ✅ 由权威宿主天然承担 |
| 输入 / 状态记录（重连、复盘） | ✅ 需要（输入帧） | ✅ 需要（命令流水 + 快照） |
| 不信任客户端所需的中立校验方 | ❌ 结构上做不到（人人都有全局状态） | ✅ 专用服务器可做到；房主模式做不到 |

**结论：帧同步省掉的是"权威逻辑服务器"（CPU 与状态存储的大头），不是全部服务器。** 局域网内可以做到完全 P2P；公网上通常仍需信令与中继兜底，否则相当一部分玩家根本连不上。

#### 三种部署拓扑（★ = 本项目当前阶段的选择）

| 拓扑 | 权威运行时位置 | 反作弊 | 成本 | 适用 |
| --- | --- | --- | --- | --- |
| **A. 专用服务器** | 独立 `Card.Server` 进程（中立第三方） | 中—高 | 需部署与运维 | 正式 PVP、竞技向 —— **本阶段不做，仅预留接口** |
| **B. 房主模式（Listen Server）★** | **房主玩家的客户端进程** | 低（房主即对手） | **零**（不需要任何服务器） | 本机双开验证、局域网、朋友间对战、MVP |
| **C. 混合** | 默认房主模式，需要时切专用服务器 | 视模式而定 | 中 | 未来产品化路径 —— **本阶段不做** |

> **本阶段范围（已决定）**：只实现 `LocalHost`（PVE）与 `PeerHost`（房主模式），并且在**同一台 PC 上用两个进程**验证。
> 传输只需要能跑通回环（127.0.0.1）与可选局域网，因此**不需要匹配服务、NAT 穿透、中继，也不需要引入网络库**（见 3.3）。
> 专用服务器相关的一切（`DedicatedHost`、`Card.Server` 独立部署、服务端运维）**全部推迟**，本阶段只保留接口与目录规划。

#### 房主模式（用一个客户端当服务器）可行吗？可行，但有四个必须承认的代价

1. **房主能看到对手手牌，也能改状态。** 这是最致命的一点：房主进程里就持有权威状态，视野裁剪对它形同虚设。所以**房主模式不适合竞技向 PVP**，只适合休闲、朋友间对战，或作为 MVP 的过渡形态。
2. **延迟不对称。** 房主本地几乎零延迟，对手要承受完整 RTT。回合制卡牌游戏对此不敏感，但公平性上应有心理预期。
3. **房主退出 = 对局结束。** 除非额外实现"主机迁移"（把快照 + 命令流水交给对手，由对手接管）。在回合制 + 状态可序列化的架构下，主机迁移是**可行的**（比实时游戏容易），但属于 P2 工作量。
4. **公网对战仍需大厅 / 信令 / 中继。** 玩家设备通常处于 NAT 后、防火墙或移动网络，对手不一定能直连房主。**本项目当前阶段不涉及公网**，因此这一项暂不需要；等到要做公网对战时再补（届时可用轻量信令 + 中继，或直接切专用服务器）。

#### 架构结论（本项目的处理方式）

**权威运行时只实现一份，作为共享库存在；"跑在哪里"只由宿主决定。**

- 权威对局运行时 `MatchHost` 放在**共享 BCL 层**（`Card.Application`），不放在服务端专属工程里。
- 宿主抽象为 `IMatchHost`：`LocalHost`（PVE，进程内，M6 已具备）、`PeerHost`（房主模式，**本阶段实现**）、`DedicatedHost`（专用服务器，**本阶段只留接口**）。
- **禁止**为房主模式另写一套规则或简化校验——必须复用同一个 `MatchHost` 与 `RuleEngine`。

> 这条设计让"本机验证 → 局域网 → 公网/专用服务器"成为**配置切换**，而不是重写。对应 [00 ADR-16](./00-现状解构与架构再设计.md)。

### 2.3 对阶段一的净影响

| 项 | 阶段一是否受影响 |
| --- | --- |
| "逻辑层零浮点/零系统时间"硬约束 | **取消**（不再需要） |
| `Card.Domain` 零 `UnityEngine` 依赖 | **保留并加强**（服务器要复用同一份代码） |
| 所有操作走 `GameCommand` | **保留**（上行内容就是命令） |
| 状态/事件可序列化 | **新增要求**（快照与增量的前提） |
| 随机数可注入种子 | **保留但降级为"可测试性要求"**（不再需要双端逐位一致） |
| 对局录制回放 | **保留**（改由服务器记录命令流水与事件，用于复盘与排查） |

## 3. 架构与模块

### 3.1 全局结构

```
            ┌──────────────── 同一台 PC（两个进程）────────────────┐
            │                                                     │
┌───────────▼──────────┐  127.0.0.1 回环  ┌──────────────────────▼──────┐
│ 实例 A：房主 + 玩家1 │◄────────────────►│ 实例 B：玩家 2（客户端）      │
│ ──────────────────── │  命令上行         │ ─────────────────────────── │
│ Presentation（对战UI）│  状态下发         │ Presentation（对战 UI）      │
│ Card.Network          │                  │ Card.Network                │
│   PeerHost（监听）    │                  │   NetworkMatchClient        │
│   LocalClientSession  │                  │   CommandUplink             │
│ MatchHost（权威）     │                  │   StateApplier / Interpolator│
│   ├─ 命令校验          │                  │   CommandRejected 提示        │
│   ├─ 权威状态推进      │                  │                             │
│   ├─ 视野裁剪          │                  │  MatchHost 只跑在 A 侧        │
│   └─ 快照 / 增量        │                  │                             │
└───────────────────────┘                  └─────────────────────────────┘
```

> 两个实例是**同一个构建**（或"编辑器 + 独立构建"），通过启动参数或界面选择"当房主 / 加入"。
> `MatchHost` 只在房主进程里跑；玩家 2 收到的是裁剪后的状态。
> 将来切专用服务器时，只需把 `MatchHost` 从 A 侧搬到独立进程，两侧的客户端代码与规则代码都不变。

### 3.2 两侧职责边界（重要）

| 职责 | 权威宿主（专用服务器或房主） | 客户端 |
| --- | --- | --- |
| 规则校验与结算 | ✅ 唯一执行者 | ❌ 禁止 |
| 随机数生成 | ✅ | ❌ |
| 隐藏信息（对手手牌、牌库顺序） | ✅ 持有全量（**房主模式下这是它最大的弱点**，见 2.4） | 只持有服务器下发的可见子集 |
| 玩家意图采集 | 接收 | ✅ 产生 `GameCommand` |
| 状态渲染与动画 | ❌ | ✅ |
| 预测（可选） | ❌ | ✅ 本地临时推演，收到权威状态后纠正 |
| 断线重连 | ✅ 下发快照 + 增量 | 请求重连并应用 |

> **一句话检验标准**：任何"能改变对局结果"的计算，只能发生在权威宿主。
> 客户端本地唯一允许的计算是**预测**——它只驱动表现，且必须能被一次和解完全撤销。

### 3.3 程序集与源码共享

| 程序集 | 位置 | 用途 | 可被谁引用 |
| --- | --- | --- | --- |
| `Card.Core` | `Assets/_Project/0_Core` | 基础工具 | 全部 |
| `Card.Domain` | `Assets/_Project/1_Domain` | 规则与状态模型（**唯一真相**） | 全部，且被服务器直接引用 |
| `Card.Application` | `Assets/_Project/2_Application` | 用例编排、命令定义、对外接口、**权威对局运行时 `MatchHost`** | 全部（客户端与服务器共用） |
| `Card.Network` | `Assets/_Project/2_Network` | 客户端网络实现 + **本阶段的宿主实现（`PeerHost` / `LocalHost`）** | 仅 Bootstrap |
| `Card.Server` | `Server/Card.Server`（Unity 工程外） | 专用服务器宿主外壳 —— **本阶段不实现，仅保留规划** | 独立进程（未来） |
| `Card.Presentation` | `Assets/_Project/4_Presentation` | 表现层 | — |
| `Card.Bootstrap` | `Assets/_Project/5_Bootstrap` | 组装 | — |

**关键点：权威运行时是"库"，不是"服务端程序"。** `MatchHost` 与 `RuleEngine` 位于共享层，因此：

- **本阶段（房主模式）**：客户端进程引用同一份共享层，`MatchHost` 跑在房主客户端内，对手通过 `Card.Network` 连接。
- 本地 PVE：`MatchHost` 直接跑在客户端进程内，不需要任何网络。
- （未来）专用服务器：`Card.Server` 进程引用共享层，`MatchHost` 跑在服务端进程。

三种情况的规则代码与校验逻辑**完全一致**，"跑在哪里"由 Bootstrap 按配置选择宿主实现。
本阶段只需要实现前两种，第三种留接口。

#### 传输选型：本阶段可以不引入任何网络库

| 场景 | 建议实现 | 理由 |
| --- | --- | --- |
| 本机双进程（回环） | `BclTcpTransport`：`System.Net.Sockets.TcpListener` / `TcpClient` + 长度前缀消息 | 零新依赖、零包体增加、不需要 ADR、跨平台且足够可靠 |
| 局域网（可选验证） | 同一个 `BclTcpTransport`，监听 `0.0.0.0`，对手填房主内网 IP | 不需要 NAT 穿透，路由器同一网段即可 |
| 公网（未来） | 届时再评估 UDP / WebSocket / Unity Transport + 中继 | 需要 NAT 穿透与中继，属未来话题 |

> **结论：本阶段不引入第三方网络库。** 消息层只需保证"可靠有序 + 长度前缀 + 协议版本"，TCP 已经满足；
> 这样可以把精力全部放在"权威 + 状态同步"的正确性上。等到做公网时再走 ADR 重新选型。

**（未来）源码共享方式**：`Card.Server` 的 `.csproj` 通过通配符直接编译 `0_Core`、`1_Domain`、`2_Application` 目录下的源码：

```xml
<ItemGroup>
  <Compile Include="..\Assets\_Project\0_Core\**\*.cs" />
  <Compile Include="..\Assets\_Project\1_Domain\**\*.cs" />
  <Compile Include="..\Assets\_Project\2_Application\**\*.cs" />
</ItemGroup>
```

**由此产生的硬约束**：这三个目录**只能依赖 BCL**（.NET 标准库）。

```csharp
// ❌ 违规：Domain 引用 UnityEngine → 服务器无法编译
using UnityEngine;
public sealed class CardInstance : MonoBehaviour { }

// ❌ 违规：Application 依赖 Unity 的序列化/日志/时间
using UnityEngine;   // Debug.Log、Time.time、JsonUtility

// ✅ 正确：只用 BCL 与自定义抽象
using System;
using System.Collections.Generic;
```

| 需求 | 允许的实现 | 不允许 |
| --- | --- | --- |
| 日志 | `Card.Core` 的 `GameLog`（抽象 + 注入实现） | `UnityEngine.Debug` |
| 时间 | `IClock` 抽象 | `DateTime.Now` / `Time.time` |
| 随机 | `IRandomProvider`（服务端注入种子） | `UnityEngine.Random` 直接调用 |
| 序列化 | `System.Text.Json` / 自定义二进制（服务端与客户端同一实现） | `JsonUtility` / `ScriptableObject` |

### 3.4 核心类清单

**权威侧（共享层 `Card.Application`，三种拓扑共用）**

| 类型 | 职责 |
| --- | --- |
| `MatchHost` | 每局对局的权威运行时：tick 循环、命令队列、权威状态推进 |
| `CommandValidator` | 调用 `RuleEngine.Validate`；拒绝非法命令并记录原因 |
| `PlayerViewProjector` | **视野裁剪**：为每位玩家生成只含其可见信息的状态视图（唯一裁剪入口） |
| `SnapshotBuilder` | 生成全量快照（重连 / 首次进入用）与增量补丁 |
| `MatchRecorder` | 记录命令流水与关键事件（回放、复盘、申诉） |

**宿主（`IMatchHost` 抽象；本阶段实现前两个）**

| 类型 | 职责 | 本阶段 |
| --- | --- | --- |
| `LocalHost` | PVE / 离线宿主：进程内直接驱动 `MatchHost`，不使用网络 | ✅ 已具备（M6） |
| `PeerHost` | 房主模式：由房主客户端启动 `MatchHost` 并监听，对手连入 | ✅ 实现 |
| `DedicatedHost` | 专用服务器宿主：进程启动、监听、对局生命周期 | ⬜ 只留接口 |

## 4. 权威模型

> 本节中的"权威侧 / 权威宿主"在本阶段就是**房主客户端进程**；将来切专用服务器时，同一套逻辑跑在 `Card.Server` 进程里。

### 4.1 一次操作完整时序

```
客户端                                    权威宿主（本阶段 = 房主进程）
  │ 玩家点击"出牌"                          │
  ├─ UI 立即反馈（表现先行，可撤销）          │
  ├─ CommandUplink 发送 PlayCardCommand ───►│
  │                                         ├─ 1. 校验会话与回合归属
  │                                         ├─ 2. RuleEngine.Validate（费用/目标/场位/嘲讽…）
  │                                         │      └─ 非法 → 回 CommandRejected(原因)，状态不变
  │                                         ├─ 3. Apply → 修改权威状态
  │                                         ├─ 4. 结算随机（服务器随机源）
  │                                         ├─ 5. 生成事件 + 状态增量
  │                                         ├─ 6. PlayerViewProjector 按玩家裁剪
  │◄──── CommandAccepted(含序号) ───────────┤
  │◄──── StateDelta(可见子集) + Events ─────┤
  ├─ StateApplier 应用 → 通知表现层           │
  └─ 与本地预测不一致 → 和解（纠正显示）        │
```

### 4.2 权威边界规则

1. **客户端不跑规则。** `RuleEngine` 在客户端仅用于两种例外：① PVE 本地对局；② PVP 的**可选预测**（预测结果永不作为最终结果）。
2. **命令必须自证来源。** 每条上行命令带：会话令牌、命令序号、目标回合号；服务器丢弃不匹配的命令。
3. **服务器不信任任何客户端状态。** 客户端上报的只有"意图"，不上报状态。
4. **服务端 tick 与客户端帧率解耦。** 服务器按固定 tick 推进（10 Hz）；无命令时只做心跳与超时检查。
5. **幂等与顺序。** 命令按序号处理，重复命令（重发）被识别并只执行一次。

### 4.3 服务器 tick 做什么

| tick 内动作 | 说明 |
| --- | --- |
| 处理到达的命令 | 校验 → 结算 → 收集事件 |
| 推进计时类逻辑 | 回合超时、动画无关的延迟效果（如"2 回合后生效"） |
| 生成状态增量 | 只包含本 tick 发生变化且对该玩家可见的字段 |
| 心跳与超时 | 检测掉线、触发重连窗口 |
| 周期快照 | 每 N tick 生成一次全量快照，供重连与校验使用 |

> 注意：**动画、音效、粒子、插值都不是服务器的事**。服务器只产出"发生了什么"。

## 5. 状态同步机制

### 5.1 同步什么、不同步什么

| 内容 | 同步方式 |
| --- | --- |
| 对局状态（英雄生命、法力、场面、手牌可见部分、牌库数量…） | 状态快照 + 增量 |
| 状态变化的因果（"造成了 3 点伤害"） | 事件（供表现层播动画与日志） |
| 玩家的意图 | 上行命令 |
| 动画进度、粒子、镜头、UI 布局 | **不同步**（纯本地表现） |
| 对手手牌内容、牌库顺序 | **不下发**（视野裁剪） |

### 5.2 快照与增量

```csharp
/// <summary>全量快照：用于首次进入与断线重连。体积可控（卡牌游戏状态很小）。</summary>
public sealed class MatchSnapshot
{
    public int SnapshotId { get; init; }
    public int ServerTick { get; init; }
    public int TurnNumber { get; init; }
    public int ActingPlayerId { get; init; }
    public PlayerView LocalPlayer { get; init; }     // 含自己的手牌明细
    public PlayerView OpponentView { get; init; }    // 对手手牌只有数量
    public ulong StateVersion { get; init; }         // 单调递增，用于拒绝过期包
}

/// <summary>增量补丁：只带变化的字段，带上基于的版本号。</summary>
public sealed class StateDelta
{
    public int BasedOnVersion { get; init; }
    public ulong NewVersion { get; init; }
    public IReadOnlyList<StateChange> Changes { get; init; }
    public IReadOnlyList<GameEventView> Events { get; init; }
}
```

规则：

1. **版本号单调递增**：客户端丢弃 `NewVersion <= 本地版本` 的包（重复包），发现 `BasedOnVersion` 与本地不符时**请求快照**（不允许"猜着合并"）。
2. **每条 delta 必须可独立重放**：包含基于版本 + 目标版本，便于乱序检测。
3. **状态与事件分开**：状态用于渲染当前画面，事件用于播放过程。两者都来自同一次权威结算。

### 5.3 视野裁剪（本方案的核心优势）

服务器为每位玩家生成**不同的**状态视图：

```csharp
public interface IPlayerViewProjector
{
    /// <summary>按观察者视角裁剪权威状态：隐藏信息只保留数量与标识，不保留内容。</summary>
    MatchSnapshot Project(MatchState authoritative, int observerPlayerId);
}
```

| 信息 | 自己 | 对手 |
| --- | --- | --- |
| 手牌明细 | ✅ 完整下发 | ❌ 只下发数量与背面标识 |
| 牌库顺序 | ❌ 不需要（客户端不推演） | ❌ 只下发剩余数量 |
| 场面随从 | ✅ 完整 | ✅ 完整（场上信息本就是公开的） |
| 坟场 | ✅ 完整 | ✅ 完整 |
| 英雄生命/护甲/法力 | ✅ | ✅ |
| 对手已打出的牌 | ✅（打出即公开） | ✅ |

> 这直接解决了帧同步最棘手的问题：**客户端内存里根本不存在对手手牌的内容**，无需依赖"看不到就行"的遮挡。

### 5.4 事件驱动发布（避免空包）

回合制游戏不需要每 tick 都发状态：

| 情况 | 行为 |
| --- | --- |
| 无状态变化 | 只发心跳（极低成本） |
| 有命令被接受 | 发增量 + 事件 |
| 回合切换 | 发增量（法力、抽牌、回合标记） |
| 定期 | 每 N tick 发一次轻量校验包（版本号 + 摘要），便于发现丢失 |

### 5.5 客户端插值

服务器 10 Hz，客户端 60 FPS，因此表现层必须插值：

| 表现 | 处理 |
| --- | --- |
| 生命值/法力数字 | 数值 Tween，不做瞬时跳变 |
| 随从位置/进出场 | 位置插值 + 动画状态机 |
| 抽牌 | 事件到达后播放翻牌动画 |
| 回合横幅 | 事件触发 |

**原则**：表现可以慢慢播，**逻辑状态以服务器最后一次确认为准**。

## 6. 客户端预测与和解

### 6.1 基础版本（M13 交付，必须有）

| 特性 | 做法 | 玩家感受 |
| --- | --- | --- |
| 表现先行 | 点击出牌时本地立即播放"卡牌飞向战场"动画，但**不改本地状态** | 操作即时反馈 |
| 等待确认 | 收到 `CommandAccepted` 后把卡牌正式落位 | 约 200–300 ms |
| 被拒绝时回退 | 收到 `CommandRejected` 时卡牌飞回手牌 + 提示原因 | 明确、可理解 |

回合制卡牌游戏用这个版本就足够，**不需要回滚同步**。

### 6.2 增强版本（本阶段不做，留作未来）

> 本机回环延迟接近 0，**不需要预测与和解**。以下内容仅在未来做公网对战时才考虑，因此从 M14 移出。

```csharp
public interface ILocalPredictor
{
    /// <summary>本地临时推演（不产生副作用），仅用于表现层预测。</summary>
    PredictedOutcome Predict(IGameCommand command, ClientMatchView currentView);

    /// <summary>收到权威状态后对比并纠正表现层。</summary>
    void Reconcile(MatchSnapshot authoritativeSnapshot);
}
```

限制：

1. 预测结果**永不写入**本地状态容器，只驱动表现。
2. 预测必须能在一次和解中完全撤销（表现层要支持"回退动画"）。
3. 随机相关的结果（如"随机造成 2–3 点伤害"）**不预测**，等待服务器。
4. 若预测频繁失败并造成视觉抖动，直接关闭预测（保留基础版本）。

## 7. 反作弊与安全

> **本阶段（本机房主模式验证）明确不做反作弊。** 房主即对手，能看到手牌、能改状态，这是房主模式的固有属性。
> 本节描述的是"架构本身能提供什么"以及"将来上专用服务器时能补到什么程度"，**不是本阶段的验收要求**。

### 7.1 权威结构能防住什么（相对于玩家 2 而言）

| 作弊手段 | 对非房主一方是否被防住 | 机制 |
| --- | --- | --- |
| 直接改本地状态（改血量、改法力） | ✅ | 本地状态只用于显示，房主不认可 |
| 看到对手手牌 | ✅ | 房主侧裁剪后才下发，客户端不持有该数据 |
| 提前行动 / 跳过回合 | ✅ | 房主校验回合归属与命令序号 |
| 使用不存在的卡 / 非法目标 | ✅ | 房主侧 `RuleEngine.Validate` |
| 重放旧命令（重复发包） | ✅ | 命令序号 + 幂等处理 |
| 刷请求（高频发包） | ✅ | 速率限制 + 命令队列上限 |
| 自动出牌脚本（脚本化操作） | ⚠️ 部分 | 只能通过行为检测与频率限制缓解 |
| 多开 / 双人共谋 | ❌ | 属运营问题，不在本设计范围 |
| 抓包分析对手信息 | ✅ | 下发的就是裁剪后的数据，抓包也拿不到手牌 |
| **房主本人作弊**（看牌、改状态、改随机） | ❌ **无防护** | 房主进程持有全部权威状态 |

### 7.2 安全等级声明

- **本阶段：不做反作弊**，仅用于本机功能验证。产物不得对外分发或用于公开对战。
- 架构上，非房主一方无法通过改本地数据影响结果；这一点在验证时值得用一个测试确认（属于 M13 的作弊注入测试）。
- 若将来要做公开对战：升级为专用服务器（ADR-16 的拓扑 A），可获得"中—高"强度；仍不是电竞级，不承诺防住脚本化操作、多开、共谋、DDoS。

### 7.3 权威侧必须做的校验清单（无论跑在房主还是服务器上）

- [ ] 会话令牌有效且属于该对局
- [ ] 命令序号单调、可去重
- [ ] 当前是否轮到该玩家（回合归属）
- [ ] `RuleEngine.Validate` 全部通过
- [ ] 请求频率在阈值内（防刷）
- [ ] 命令长度与字段范围合法（防畸形包）
- [ ] 对局是否已结束（结束后拒绝一切命令）

## 8. 断线、重连与异常

### 8.1 重连流程（快照 + 增量）

```
客户端断线（网络抖动 / 进程重启 / 切后台）
  → 重连请求（会话令牌 + 对局 Id + 本地最后版本号）
  → 服务器校验：对局仍在进行、令牌有效、重连窗口未超时
  → 服务器下发：全量快照（按该玩家视角裁剪）+ 之后产生的增量
  → 客户端清空本地视图 → 应用快照 → 应用增量 → 恢复到最新版本
  → 若重连超时：判定掉线（见 8.2）
```

要点：

1. 快照本身必须**按玩家视角裁剪**（重连不能成为绕过视野裁剪的通道）。
2. 重连期间服务器**继续正常推进**对局（例如等待对手操作），或按规则暂停（本设计采用"继续推进 + 超时判负"）。
3. 重连失败不崩溃：给出明确提示并返回大厅。

### 8.2 掉落与超时判定

| 情况 | 判定 |
| --- | --- |
| 玩家离线 < 重连窗口（默认 30 s） | 允许重连；对手看到"对手重连中" |
| 离线 > 重连窗口 | 判掉线，该玩家判负，对手获胜 |
| 回合内操作超时（默认 75 s） | 自动结束回合（可配置为判负） |
| 双方同时掉线 | 该局作废 |
| 主动投降 | 立即判负，正常结算 |
| 服务器异常 | 该局作废；客户端返回大厅并提示，不卡在"等待中" |

### 8.3 异常处理原则

1. 所有网络异常都要有**明确终态**（判负 / 作废 / 返回大厅），不允许无限等待。
2. 所有异常都要写日志，并能关联出对局 Id 与版本号。
3. 客户端在任何异常下都不得崩溃，也不得出现"能操作但服务器不响应"的假活状态（超过阈值即提示并锁定 UI）。

## 9. 协议与生命周期

### 9.1 消息列表（本机/局域网直连版）

| 方向 | 消息 | 载荷要点 |
| --- | --- | --- |
| C→S | `Hello` | 协议版本、玩家名、卡组摘要（**无需账号与会话令牌**） |
| C→S | `Ready` / `Leave` | 准备状态 / 主动退出 |
| C→S | `Command` | 命令序号、目标回合、`GameCommand` 内容 |
| C→S | `SnapshotRequest` | 本地版本号（版本冲突时请求） |
| C→S | `ReconnectRequest` | 对局 Id、本地最后版本号（直连重连） |
| C→S | `Ping` | 时间戳（RTT 统计） |
| S→C | `HelloAck` / `RoomState` | 协议版本确认、房主玩家、准备状态 |
| S→C | `MatchStart` | 对局 Id、双方英雄、先手方、协议版本、权威 tick |
| S→C | `CommandAccepted` / `CommandRejected` | 命令序号 / 拒绝原因（对应 `CommandError`） |
| S→C | `StateDelta` | 基于版本、新版本、变化列表、事件列表 |
| S→C | `MatchSnapshot` | 按玩家裁剪的全量快照 |
| S→C | `MatchEnd` | 胜负、结束原因（正常/掉线/投降/房主退出） |
| S→C | `Error` | 错误码与说明（含协议版本不匹配） |

> 本阶段**没有**匹配、房间列表、排队、中继相关消息：房主启动后显示"本机地址:端口"，玩家 2 直接填入连接。

### 9.2 对局生命周期

```
Disconnected → Connecting（连接房主地址） → InRoom(Waiting) → InRoom(Ready)
    → MatchStarting（MatchStart + 初始快照）
    → MatchRunning（命令上行 / 状态下行）
         ├─ Reconnecting（快照 + 增量恢复）
         └─ MatchEnded（胜负 / 掉线 / 投降 / 房主退出）
    → InRoom / Disconnected
```

> 本阶段**没有匹配流程**：房主进程启动后进入 `InRoom(Waiting)` 并显示监听地址；玩家 2 通过地址直连。

### 9.3 协议演进

1. 协议带 `protocolVersion`；客户端与服务器版本不匹配时**明确拒绝并提示更新**。
2. `GameCommand` 与 `StateChange` 的字段增删遵循"只加不删、新增字段可选"原则。
3. 状态结构变更时提升 `schemaVersion`，并为旧客户端保留明确的拒绝路径。

## 10. 性能预算

### 10.1 带宽估算（事件驱动）

| 项 | 估算 |
| --- | --- |
| 上行单条命令 | 约 20–40 字节 |
| 下行单次状态增量 | 约 100–400 字节（含事件） |
| 单局下行总量 | 约 30–150 KB（一局 20 次左右操作） |
| 心跳 | 10 Hz × 约 20 字节 ≈ 0.2 KB/s |

结论：带宽压力可忽略。本阶段跑回环，流量与延迟都不构成约束；等到做公网时再关注 RTT 与丢包。

### 10.2 延迟预算

| 项 | 目标 |
| --- | --- |
| **本机回环 RTT** | **≤ 5 ms** |
| 局域网 RTT（可选验证） | ≤ 50 ms |
| 操作到权威确认（本机） | ≤ 100 ms（主要是权威 tick 间隔） |
| 操作到本地表现反馈 | ≤ 1 帧（表现先行） |
| 重连恢复 | ≤ 3 s |
| 裁剪后快照体积 | ≤ 8 KB |

### 10.3 本机验证资源目标

| 指标 | 目标 |
| --- | --- |
| 双实例同时运行 | 单机 ≥ 60 FPS（低配机 ≥ 30 FPS 可接受） |
| 单局额外内存（房主侧） | ≤ 20 MB（含两个实例的对局数据） |
| 建立连接耗时 | ≤ 1 s（回环） |
| 同时验证的对局数 | 1 局（本阶段不需要并发压测） |

| --- | --- | --- |
| 权威侧单元测试 | `Card.Application` 的 NUnit 测试，**不启动 Unity** | `MatchHost` 命令校验、状态推进、增量生成 |
| 共享内核测试 | 复用阶段一的 `Card.Tests.EditMode` | 规则正确性（客户端与权威侧共用同一份测试） |
| 裁剪测试 | 断言"对手视角中不含手牌明细与牌库顺序" | 防止裁剪逻辑写漏（防止玩家 2 拿到不该拿的数据） |
| 进程内双端测试 | `InMemoryTransport` 直连 `MatchHost`（无需真实网络） | 命令上行、状态下行、版本冲突 |
| **本机双进程测试（本阶段主验证手段）** | 两个进程通过 `127.0.0.1` 回环连接，完整打完一局 | 端到端流程、UI、重连、异常提示 |
| 消息异常注入 | 乱序、重复、超长、非法字段、版本不匹配 | 拒绝且不崩溃 |
| 重连测试 | 在随机时刻断开玩家 2 并重连 | 快照 + 增量恢复正确 |
| 作弊注入测试 | 玩家 2 侧伪造非法命令、重复命令、越权命令、超频请求 | 全部被房主拒绝且状态不变 |
| Soak 测试 | 连续 30 局 + 长时间挂机 | 无内存、连接、句柄泄漏 |

**门禁要求**：

1. 权威侧单元测试必须能在**无 Unity 环境**运行（这是内核解耦的直接验证）。
2. **本机双进程端到端跑通一局**，是阶段二的主要验收手段。
3. 裁剪测试失败按 **P0** 处理（会导致玩家 2 拿到不该看到的数据）。

### 13.1 阶段一必须完成的"预留清单"（现在就要做的）

> 相比帧同步方案，这份清单**显著变短**：不再要求零浮点、不再要求固定遍历顺序、不再要求跨平台逐位一致。

- [ ] `Card.Core` / `Card.Domain` / `Card.Application` **只依赖 BCL**，不引用 `UnityEngine`（asmdef 强制）
- [ ] 日志 / 时间 / 随机通过抽象注入（`GameLog` / `IClock` / `IRandomProvider`），不直接调用 Unity API
- [ ] 所有玩家与 AI 操作走 `GameCommand`，且命令可序列化
- [ ] `MatchState` 设计为**可序列化、可裁剪、可增量**（不散落依赖 UI 的引用）
- [ ] 状态变更统一产出 `GameEvent`（既供表现，也是状态同步的事件来源）
- [ ] 对局可记录"命令流水 + 关键事件"（回放与排查用）
- [ ] `Card.Network` 目录 / 程序集已建立（可为空，但依赖关系已约束）；`Server/Card.Server` 只保留规划，不在本阶段建立

## 14. 与帧同步方案（1.0 版）的变更说明

### 14.1 被撤销的结论

| 旧结论（帧同步） | 现结论（状态同步） |
| --- | --- |
| 逻辑层必须零浮点，用 `int` / `Fix64` | **撤销**。允许浮点；规则层仍建议优先用整数，理由是便于测试与显示一致 |
| 禁止 `Time` / `DateTime`，只用逻辑 tick | **部分撤销**。规则层建议不依赖时间，但不再是强制扫描项 |
| 必须固定集合遍历顺序 | **撤销**（服务器单点结算，不存在双端一致性问题） |
| 必须跨平台状态哈希逐位一致 | **撤销**。改为"状态可序列化 + 版本号 + 快照 / 增量" |
| 网络只传输入帧 | **改变**。上行传命令，下行传服务器产出的状态与事件 |
| 隐藏信息靠客户端遮蔽 | **升级**。改由服务器视野裁剪，客户端不持有隐藏数据 |
| 反作弊等级低 | **提升**为中—高 |
| P2P 可行、无需服务器 | **部分撤销**。纯 P2P（人人跑规则）不可行；但"用其中一个客户端当权威宿主"（房主模式）可行，见 2.4 |

### 14.2 保留的结论

| 保留项 | 原因变化 |
| --- | --- |
| `Card.Domain` 零 `UnityEngine` 依赖 | 从"确定性"变为"服务器可复用同一份规则代码"——**要求更强** |
| 所有操作走 `GameCommand` | 从"输入帧同步"变为"命令上行" |
| 命令与状态可序列化 | 变为**更强的要求**（快照、增量、重连的基础） |
| 随机数可注入种子 | 降级为"可测试性 + 服务器随机源"要求 |
| `Card.Network` 独立且可移除 | 不变（PVE 不依赖网络） |
| 对局录制 | 不变，但内容变为"命令流水 + 关键事件" |

## 15. 版本 3.0：收敛为"本机房主模式验证"

### 15.1 本次收敛的原因

目标是**用最低成本先验证双人联网能跑通**，而不是上线运营。于是把范围收缩到：

- 不需要服务器采购与运维；
- 不需要匹配服务、账号体系、NAT 穿透、中继；
- 不需要反作弊、不需要预测与和解；
- 传输甚至可以完全不引入第三方网络库（用 BCL 的 TCP）。

代价是：**房主即对手，房主可以看牌与改状态**；并且**本机回环几乎无延迟丢包**，结论不能直接外推到公网。这两点在文档中已明确标注。

### 15.2 相对 2.0 版（全量状态同步方案）被削减的内容

| 项目 | 2.0 版 | 3.0 版（当前） |
| --- | --- | --- |
| 部署拓扑 | 专用服务器 / 房主 / 混合 | **只做 `LocalHost` + `PeerHost`** |
| 连接范围 | 公网 | **本机回环为主**，局域网可选 |
| 匹配与房间 | 快速匹配 + 房间列表 | **手动直连**（房主显示地址，玩家 2 填入） |
| 传输 | 评估 Unity Transport 等 | **BCL TCP + 长度前缀，零新依赖** |
| 反作弊 | 中—高（专用服务器） | **不做**（仅验证功能） |
| 客户端预测 | M14 可选实现 | **不做**（回环无延迟，无必要） |
| 主机迁移 | P2 可选 | 暂不做（房主退出即对局结束） |
| 并发/运维指标 | 单机 500 局等 | 单机跑 1 局，双实例 60 FPS |
| 阶段二工期 | 22–32 人日 | **约 10–16 人日** |

### 15.3 本阶段如何验证（两条路径）

**路径 1：纯逻辑验证（不需要网络，最快）**

两个 `MatchHost` + `InMemoryTransport` 跑在同一个进程里（M4-T10 已经做过雏形）。
用于验证：命令校验、状态增量、裁剪、重连逻辑。这一层应该做成自动化测试，每次提交都跑。

**路径 2：真机双进程验证（本阶段的主要验收手段）**

Unity 同一个工程**不能双开编辑器**（工程目录有锁文件），所以用以下任一方式：

| 方式 | 做法 | 适合 |
| --- | --- | --- |
| 编辑器 + 独立构建（推荐） | 编辑器里选"当房主"；另做一个 Windows 构建，选"加入"，地址填 `127.0.0.1:端口` | 日常开发调试，能看到两边日志 |
| 两个独立构建 | 出两次构建（或用一个构建 + 命令行参数区分角色，如 `-host` / `-join 127.0.0.1`） | 最接近真实运行；适合验收 |
| 局域网两台设备 | 房主监听 `0.0.0.0`，对手填房主内网 IP | 可选，验证真实网络路径 |

**角色切换方式**：用一个启动参数或一个调试面板决定 `LocalHost` / `PeerHost` / `JoinClient`，避免维护两份构建配置。

**验收动作清单（手动）**

1. 房主启动 → 界面显示监听地址与端口
2. 玩家 2 填入地址连接 → 双方进入准备状态
3. 开始对局 → 双方各看到自己 3 张起手牌，且**玩家 2 界面上看不到房主的手牌内容**
4. 双方交替出牌 / 攻击 → 两边画面一致，回合归属正确
5. 中途关闭玩家 2 → 房主提示"对手掉线"，玩家 2 重开后能重连并恢复画面
6. 打完一局 → 双方都出现胜负结算

### 15.4 未来要上公网时必须补的内容（不在本阶段）

1. 传输选型与 NAT 穿透 / 中继（Q-2）——否则相当比例玩家连不上。
2. 抖动与丢包下的重连与状态恢复验证（本机测不出来）。
3. 反作弊：升级为专用服务器（ADR-16 拓扑 A）。
4. 匹配与房间服务、账号体系。
5. 预测与和解（仅在公网延迟下手感不足时才需要）。
