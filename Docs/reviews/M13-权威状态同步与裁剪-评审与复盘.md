## 6. 问题与根因（5 Why）

### 现象 1：心跳超时误判——积压消息被判为掉线（M13-T8-B1）

- Why1：T8 回合超时测试在压力下偶发掉线断链，单跑通过、全量跑失败；
- Why2：`PeerSession.Pump` 先做心跳超时判定、后处理积压消息——"消息已到达但 ReceiveLoop 线程尚未入队完成"被算进 idle；
- Why3：T7 实现心跳时默认 Pump 与 ReceiveLoop 同步推进，未考虑跨线程入队延迟；
- **根因**：**超时语义写成了"自上次 Pump 以来"而非"自上次收到消息以来"**——判定必须发生在消息处理之后。
- 处置：Pump 重排（处理积压 → 判定超时 → 发心跳）+ 测试夹具 AdvanceIdle 分批快进加保活；T9 拆分后该顺序以 `PumpReceivedFrames → RunHeartbeat` 结构固化。

### 现象 2：终态编排二次超时永远差 1 tick（T8 自查推演发现）

- Why1：AC-3 断言 version=2 按推演必失败；
- Why2：代发 EndTurn 后未同步 `_lastSeenVersion`，下一 tick 版本检测把 `_turnStartTick` 重置为 now，第二次 750 tick 永远差 1；
- **根因**：**"代发即视为一次权威状态变更"的隐含语义没有落到版本基线同步**。
- 处置：代发后同步 `_lastSeenVersion = StateVersion; _turnStartTick = CurrentTick`。

### 现象 3：未握手 Ready 可造成假开局（T9 注入矩阵发现）

- Why1：握手前注入 Ready 帧，会话直接置 PeerReady 并发 MatchStart；
- Why2：`HandleReady` 无握手门控，T5 实现开局门控时只防了 Command（MatchStarted 门）未防 Ready；
- **根因**：**状态机时序校验散落在各消息分支，缺少"每帧先过状态机合法性"的统一入口**——T9 补齐握手门与版本门后，防御集中到 Pump 前置层。
- 处置：HandleReady 握手门 + HandleHello 幂等 + 端到端注入测试固化。

### 现象 4：测试基础设施的两类时序陷阱（T7/T8 反复踩）

- 现象：TCP 回环测试单跑过、全量跑偶发失败（ReceiveLoop 线程饿死、`TryReceive(out _)` 吞帧后断言落空、Dispose 竞态 M12-B2）；
- **根因**：**真实 TCP 测试对调度压力敏感**——自旋等待必须有超时与 Sleep 让出、取帧辅助不得有副作用、快进必须分批保活。
- 处置：沉淀 `TryTakeFrame`（返回 RawMessage?，不吞帧）、AdvanceIdle 分批 ≤50 tick + Pong 保活 + Sleep(5) 等夹具模式；同类新测试直接复用。
