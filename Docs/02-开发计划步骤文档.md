# 02 开发计划步骤文档

> 版本：1.0 ｜ 状态：基线（Baseline）
> 上游依据：[01-开发需求文档](./01-开发需求文档.md)
> 本文定义**按什么顺序做、每步做完的标志是什么**。执行时严格按里程碑推进，不跳阶、不倒序。

## 1. 总体策略

### 1.1 五条执行原则

1. **先内核，后表现。** 逻辑没跑通之前不写动画。先让"规则在无 UI 环境下正确"。
2. **垂直切片优先于横向铺开。** 每个里程碑必须产生**可运行、可演示**的成果，禁止"三个模块都写了 60% 但一个都跑不起来"。
3. **永远保持主干可运行。** 任何时刻主分支都应能进入游戏并完成一次冒烟流程。
4. **测试先行于重构、伴随于开发。** 规则类先写测试用例（含边界：空牌库、满场、嘲讽、同归于尽）。
5. **一次只做一件事。** 单个任务卡范围不超过 1 个模块；超了就拆。

合计：阶段一约 **50–70 人日**，阶段二约 **10–16 人日**（单人全职整体约 3–4 个月；AI 协作下重点在评审与验证时间）。

> **范围收敛说明**：阶段二原设计包含专用服务器、匹配服务、NAT 穿透、反作弊与客户端预测，现**全部移出本阶段**（列入阶段三/未来）。
> 本阶段只做"同一台 PC 上两个进程跑通双人联网"，传输直接用 BCL TCP，零第三方网络依赖。详见 [05 第 15 节](./05-联网对战_状态同步_设计文档.md)。

> **前置约束**：M11 的所有工作都建立在"阶段一没有把规则代码与 Unity 绑死"之上。因此 M1/M3/M4/M5 的任务表里都加了"无 Unity 依赖 / 可序列化 / 事件化"要求（见各节 ★ 标记）。若阶段一违反了这些约束，M11 的工作量会从"接入宿主"变成"拆内核"。

> **方案变更说明**：阶段二原设计为确定性锁步帧同步，现改为**服务端权威状态同步**（决策记录见 [00 ADR-12](./00-现状解构与架构再设计.md) 与 [05 第 14 节](./05-联网对战_状态同步_设计文档.md)）。随之撤销了"逻辑层零浮点 / 零系统时间 / 固定遍历顺序 / 跨平台状态哈希一致"等要求，阶段一项的确定性任务相应取消或降级。

> **阶段三（未来，暂不做）**：专用服务器、公网对战、匹配服务、NAT 穿透与中继、反作弊加固、客户端预测与和解、主机迁移。这些内容已从阶段二移出，等本机验证通过后再单独立项。

### 1.3 关键路径

```
阶段一  M0 ─ M1 ─ M2 ─ M3 ─ M4 ─ M5 ─ M6 ─ M7 ─ M9 ─ M10
                              └─ M8（元游戏，可并行）
阶段二                                                        └─ M11 ─ M12 ─ M13 ─ M14
                                                                    （本机房主模式验证，依赖 M10 + FR-13）
```

**关键路径上的瓶颈是 M3/M4**（规则内核）。规则不稳，后面全部返工。因此 M3/M4 的质量门禁最严：必须有测试覆盖与评审记录。

**阶段二有一条"隐形关键路径"**：内核解耦与状态可序列化。它不在 M11 才出现，而是从 M1（日志/时间/随机抽象）、M3（状态模型可序列化、可裁剪）、M4（命令与事件模型）就开始了。评审时若发现规则层出现 `UnityEngine` 依赖，或状态里散落无法序列化的引用，按 P0 处理。

### M1 核心基础层（Core）

| ID | 任务 | 产出物 | 完成标准 |
| --- | --- | --- | --- |
| M1-T1 | `Result` / `Guard` | `Card.Core` 中的结果类型与参数校验工具 | 单测覆盖：成功、失败原因、null 输入 |
| M1-T2 | `EventBus` | 类型安全的事件订阅/发布，支持订阅者生命周期解绑 | 单测：订阅、发布、取消、异常隔离（一个订阅者抛异常不影响其他） |
| M1-T3 | `StateMachine<TState>` | 通用状态机（状态注册、进入/退出/转移校验） | 单测：合法转移、非法转移被拒、退出回调顺序 |
| M1-T4 | `IRandomProvider` ★ | 可注入种子的随机抽象（服务端随机源 + 可复现测试）+ `Shuffle` | 单测：同种子序列一致；规则层不直接调用 `UnityEngine.Random` |
| M1-T5 | `GameLog` ★ | 分通道、分等级、可开关的日志抽象（**不依赖 `UnityEngine.Debug`**） | 单测：通道过滤正确；无 Unity 依赖；可在无 Unity 进程使用 |
| M1-T6 | `ObjectPool<T>` | 通用对象池（预热、扩容上限、归还清理） | 单测：借出/归还/上限/重置 |
| M1-T7 | `ReactiveValue<T>` | 值变更通知（供 View 订阅） | 单测：变更触发、相同值不触发、取消订阅 |
| M1-T8 | `IClock` ★ | 时间抽象（逻辑取时间一律走它，便于测试与服务器复用） | 单测：可注入假时钟；规则层不直接调用 `DateTime.Now` / `Time.time` |
| M1-T9 | 内核解耦检查规则 ★ | `check.ps1` 增加"0_Core / 1_Domain / 2_Application 禁止 `UnityEngine`、禁止 Unity 专属序列化/日志"扫描 | 故意在 Domain 中 `using UnityEngine` 时，检查脚本报错 |

**M1 门禁**：Core 覆盖率 ≥ 90%；`Card.Core` 的 asmdef 无任何引用；★ 项通过"无 Unity 依赖"检查。

### 4.2 必测边界场景清单（回归基线）

1. 牌库为空时抽牌（疲劳伤害递增、不崩溃）
2. 手牌 10 张时抽牌（爆牌、不入手牌、不崩溃）
3. 战场 7 个随从时召唤（被拒绝、状态不变）
4. 法力不足时出牌（被拒绝、不扣费）
5. 嘲讽存在时攻击非嘲讽目标（被拒绝）
6. 召唤失调随从攻击（被拒绝）
7. 攻击次数用尽后再次攻击（被拒绝）
8. 双方随从同归于尽（双方都进坟场，亡语各触发一次）
9. 亡语链式触发（A 死召 B，B 战吼再触发，不死循环）
10. 英雄归零结算（胜负界面出现，后续输入被忽略）
11. 同归于尽导致双方英雄归零（判平局）
12. 配置表存在非法值（导入失败并给出精确错误位置）
13. 存档文件被手动改坏（可恢复、不崩溃）
14. 同种子抽卡/洗牌可复现
15. 状态序列化往返（含空状态、满场满手、多效果链）语义一致
16. 状态增量：无变更时产出空增量，单字段变更只产出对应变化
17. 裁剪：下发给玩家 2 的数据中不含房主手牌明细与牌库顺序（含快照与重连数据）
18. 非法/重复/越权/超频命令全部被权威侧拒绝且状态不变
19. 版本冲突或消息异常后请求快照可恢复到一致状态
20. 房主中途退出：玩家 2 得到明确终态提示，不卡在"等待中"
21. 玩家 2 中途退出：房主得到明确提示，重连窗口内可恢复

| --- | --- |

| 单文件行数 | ≤ 300 行 |
| 单方法行数 | ≤ 50 行 |
| 圈复杂度 | ≤ 15 |

| asmdef 依赖方向 | 无反向依赖 |
| 硬编码文本 | 无中文/英文字面量进入 UI（走本地化键） |

## 7. 变更管理

1. **需求变更**：先在 [01-开发需求文档](./01-开发需求文档.md) 中改 FR 与 AC，再开工；不允许"先写代码后补文档"。
2. **架构变更**：必须新增一条 ADR（写在 `00` 第 4.4 节的表中），说明背景、备选方案、影响范围、迁移成本。
3. **范围变更**：降低优先级而非删除验收标准；新增功能默认进 M9/M10。
4. **计划变更**：更新本文档里程碑表，并记录变更原因与日期。
5. 所有变更在提交信息中引用对应文档编号，例如：
   `docs(01): 明确嘲讽对英雄目标的限制 [FR-5.5]`
