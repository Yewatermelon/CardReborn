## 1. 十三条铁律（不可违反）

| # | 铁律 | 判定方式 |
| --- | --- | --- |
| 1 | **一切皆组件，组件优于继承。** 玩法差异由"数据组件 + 执行器"组合表达，禁止用继承表达卡牌种类与效果 | 出现 `class XxxCard : Card` 即违规 |
| 2 | **依赖只能向下。** 依赖方向：Core ← Domain ← Application ← Infrastructure ← Presentation ← Bootstrap | asmdef 编译期强制 |
| 3 | **Domain / Application 层不得引用 `UnityEngine`。** 规则必须能脱离 Unity 运行与测试 | asmdef 编译期强制 |
| 4 | **表现层只读不写。** View 只订阅事件并渲染，禁止判断规则、禁止修改游戏状态 | 代码评审 + 全局搜索 |
| 5 | **所有玩家/AI 操作走 `GameCommand`**，经 `RuleEngine` 校验后才生效 | 代码评审 |
| 6 | **配置驱动。** 数值、效果、卡池、关卡不在代码里硬编码 | 代码评审 + 搜索魔法数字 |
| 7 | **运行时程序集禁止出现 `UnityEditor` / `AssetDatabase` / 文件写入 `Application.dataPath`** | check.ps1 自动扫描 |
| 8 | **禁止隐式全局单例与 `Find` 查找。** 依赖通过构造函数/显式装配注入 | check.ps1 扫描 `GameObject.Find`、`FindAnyObjectByType`、`MonoSingleton` |
| 9 | **每个新功能必须带自动化测试**，规则类先写测试 | 评审门禁 |
| 10 | **单一职责、小文件。** 单文件 ≤ 300 行、单方法 ≤ 50 行、圈复杂度 ≤ 15 | check.ps1 自动扫描 |
| 11 | **内核与 Unity 解耦。** `0_Core` / `1_Domain` / `2_Application` 只依赖 BCL：禁止 `using UnityEngine`、禁止 Unity 专属日志/序列化/时间/随机；环境依赖走 `GameLog` / `IClock` / `IRandomProvider` | check.ps1 自动扫描；`Card.Server` 编译期验证 |
| 12 | **服务端权威与网络解耦。** 联网代码只能在 `Card.Network` / `Card.Server`；客户端不得直接修改权威状态，只能上行 `GameCommand`；`Card.Presentation` 不得引用 `Card.Network` | asmdef 编译期强制 + 评审 |
| 13 | **阶段范围锁。** 阶段二只做 `LocalHost` + `PeerHost`（本机双进程验证）；传输用 BCL TCP，不引入第三方网络库；不做匹配 / 账号 / NAT / 中继 / 反作弊 / 客户端预测 | 评审 + check.ps1 依赖扫描 |

> 违反铁律的代码不予合并；确有必要突破时，先在 `00` 中新增 ADR 并取得明确同意。

> 铁律 11 是**为联网 PVP（服务端权威状态同步）预留的硬性前置条件**：服务器要直接复用同一份规则源码，
> 因此规则三层只能用 BCL。它在阶段一就生效，因为一旦规则代码依赖 MonoBehaviour / JsonUtility / Unity 日志，
> 服务器就只能复制一份规则，从此长期双份维护（详见 [05 第 13.1 节](./05-联网对战_状态同步_设计文档.md)）。
>
> 注：此前版本曾要求"逻辑层零浮点 / 零系统时间 / 固定遍历顺序 / 跨平台状态哈希一致"（为帧同步服务），
> **该方案已废弃，相关约束全部撤销**，见 [05 第 14 节](./05-联网对战_状态同步_设计文档.md)。

### 3.1 类型与成员

| 元素 | 规范 | 示例 |

## 4. 代码风格

1. **缩进 4 空格**，不用 Tab；行尾不留空格；文件以换行结尾。
2. **一行一句**，禁止 `if (a) Do();` 单行写多个语句。
3. **始终使用花括号**，即使只有一行。
4. **`this.` 仅在与参数同名时使用**。
5. **类型显式**：局部变量优先 `var` 仅在类型显而易见时使用；公共 API 一律显式类型。
6. **成员顺序**：常量 → 静态字段 → 字段 → 构造函数 → 公共属性 → 公共方法 → 私有方法 → 嵌套类型。
7. **访问修饰符必须显式写出**（含 `private`）。
8. **`sealed` 优先**：不打算被继承的类加 `sealed`。
9. **不可变优先**：`readonly` / `get; private set;` / `init`，配置与命令对象应不可变。
10. **可空引用类型开启**：本项目用 `Assets/csc.rsp` 的 `-nullable:enable` 对全部程序集开启（M1-R1 落地）；
    公共 API 不接受 `null` 参数（用 `Guard.NotNull`）；测试若**故意**传 `null` 验证契约，必须写 `null!` 并保留"故意"的注释意图。
    > 注意：Unity 传给编译器的 `csc.rsp` **不支持 `#` 注释**——写注释会被当成源文件路径，导致 `CS2001/CS1504` 报错。
    > 该文件只放编译开关，说明写在本文档。
11. **不用 `#region`**。
12. **注释只解释"为什么"**，不解释"是什么"。公共 API 使用 XML 注释。
13. XML 注释与业务注释使用中文，代码标识符使用英文。

```csharp
namespace Card.Domain.Combat
{
    /// <summary>
    /// 结算一次随从/英雄之间的攻击。
    /// 规则依据：PRD 3.4（同时结算、圣盾、嘲讽校验在 RuleEngine 侧）。
    /// </summary>
    public static class CombatResolver
    {
        public static CombatResult Resolve(
            CardInstance attacker,
            ITargetable target,
            MatchState state)
        {
            Guard.NotNull(attacker, nameof(attacker));
            Guard.NotNull(target, nameof(target));
            Guard.NotNull(state, nameof(state));

            ...
        }
    }
}
```

## 5. 架构模式规范

### 5.1 组件优于继承

**表达"这张卡有什么能力"，用组合；不用继承。**

```csharp
// ❌ 违规：继承表达玩法，新增卡种必须改基类
public abstract class Card { }
public class MinionCard : Card { public int Attack; public int Health; }
public class FireballCard : MinionCard { }        // 用继承表达"火球"

// ✅ 正确：结构用类型字段区分，玩法用效果组件组合
public sealed class CardDefinition
{
    public int Id { get; init; }
    public string Key { get; init; }
    public CardType Type { get; init; }              // Minion / Spell
    public int Cost { get; init; }
    public int Attack { get; init; }
    public int Health { get; init; }
    public KeywordSet Keywords { get; init; }
    public TargetRule TargetRule { get; init; }
    public IReadOnlyList<IEffectData> Effects { get; init; }
}

// 效果是独立组件，可自由组合
public sealed class DamageEffectData : IEffectData
{
    public int Amount { get; init; }
}

public sealed class DrawCardEffectData : IEffectData
{
    public int Count { get; init; }
}
```

**判定标准**：新增一张"造成 3 点伤害并抽 1 张牌"的卡，只需在配置表里写
`Effects = DamageEffect:3 | DrawCardEffect:1`，**代码 0 改动**。

### 5.2 Definition 与 Instance 分离

| 概念 | 生命周期 | 是否可变 | 位置 |
| --- | --- | --- | --- |
| `CardDefinition` | 全局，随配置加载 | 只读 | `Card.Domain.Config` |
| `CardInstance` | 单局对局 | 可变（当前攻/血/状态） | `Card.Domain.Cards` |

```csharp
// ❌ 违规：配置对象被对局修改（旧项目的 EnemyCard 就是这样）
public class EnemyCard { public int HP; }          // 配置与状态混为一体

// ✅ 正确
public sealed class CardInstance
{
    public CardDefinition Definition { get; }
    public int CurrentHealth { get; private set; }
    public int CurrentAttack { get; private set; }
    public bool IsSummoningSick { get; private set; }

    public CardInstance(CardDefinition definition, bool isSummoningSick)
    {
        Definition = definition;
        CurrentHealth = definition.Health;
        CurrentAttack = definition.Attack;
        IsSummoningSick = isSummoningSick;
    }

    public void TakeDamage(int amount) { ... }
}
```

### 5.3 命令模式：所有操作唯一入口

```csharp
public readonly struct PlayCardCommand : IGameCommand
{
    public int PlayerId { get; init; }
    public int HandIndex { get; init; }
    public TargetRef Target { get; init; }     // 可为 None
}

public readonly struct AttackCommand : IGameCommand
{
    public int PlayerId { get; init; }
    public int AttackerBoardIndex { get; init; }
    public TargetRef Target { get; init; }
}
```

规则：

1. 命令是**不可变值对象**，只描述"意图"，不含结算逻辑。
2. 命令必须先经 `RuleEngine.Validate(command, state)` 返回 `CommandResult`。
3. 只有 `CommandResult.IsValid` 为真才允许 `RuleEngine.Apply`。
4. 人类与 AI 产出同一种命令，走同一队列。
5. 命令队列可录制/回放 —— 这是自动化回归测试与 AI 模拟的基础。

### 5.4 事件总线：逻辑与表现的唯一桥梁

```csharp
public interface IEventBus
{
    IDisposable Subscribe<TEvent>(Action<TEvent> handler) where TEvent : IGameEvent;
    void Publish<TEvent>(in TEvent evt) where TEvent : IGameEvent;
}
```

规范：

1. 事件是**过去式事实**（`CardPlayed`、`MinionDied`），不是请求。
2. 每次 `Apply` 后**批量刷新**（先结算完状态，再统一发布事件），避免表现层看到中间态。
3. 订阅必须可解绑：View 在 `OnEnable` 订阅、`OnDisable` 解绑；保存 `IDisposable` 并 `Dispose`。
4. 订阅者抛异常必须被隔离（记录日志，不影响其他订阅者与游戏状态）。
5. **禁止在事件处理器中修改游戏状态**（除明确标注的"反应型效果"通道，且须再次走 RuleEngine）。

```csharp
// ✅ View 的正确写法
public sealed class ManaView : MonoBehaviour
{
    private IDisposable _subscription;

    private void OnEnable()  => _subscription = _eventBus.Subscribe<ManaChanged>(OnManaChanged);
    private void OnDisable() => _subscription?.Dispose();

    private void OnManaChanged(ManaChanged evt)
    {
        _currentText.text = evt.Current.ToString();
        _maxText.text = evt.Max.ToString();
    }
}
```

### 5.5 状态机规范

1. 用**显式状态类**（或显式字典注册），禁止散落的 `if (phase == ...)`。
2. 状态机只负责"阶段流转"，阶段内的业务交给对应服务。
3. 非法转移必须抛错或返回失败，不得静默忽略。
4. 每个状态有明确的 `Enter` / `Exit`；`Exit` 用于清理临时状态。

```csharp
public interface ITurnPhaseHandler
{
    TurnPhase Phase { get; }
    void Enter(MatchContext context);
    void Exit(MatchContext context);
}
```

### 5.6 表现层规范

必须遵守：

| 允许 | 禁止 |
| --- | --- |
| 订阅事件、读 `MatchState` 快照 | 修改任何游戏状态 |
| 播放动画、音效、粒子 | 判断"这个操作是否合法" |
| 把用户输入转成 `GameCommand` | 直接调用领域层方法改数据 |
| 缓存 UI 引用、做布局计算 | 持有 `CardDefinition` 之外的领域对象并写回 |

```csharp
// ❌ 旧项目式的违规写法：交互组件里判断规则
if (BattleManager.Instance.gamePhase == GamePhase.player1Action && attackable)
    BattleManager.Instance.AttackConfirm(gameObject);

// ✅ 正确：只发命令，规则由 RuleEngine 判
_commandQueue.Enqueue(new AttackCommand
{
    PlayerId = _localPlayerId,
    AttackerBoardIndex = _slotIndex,
    Target = TargetRef.ForMinion(targetSlotIndex)
});
```

### 5.7 依赖注入与组合根

1. 只有 `Card.Bootstrap` 允许 `new` 具体实现与组装对象图。
2. 其他层通过**构造函数**接收依赖（`IXxx` 接口）；MonoBehaviour 通过 `AppContext` 显式注入。
3. 禁止 `ServiceLocator.Get<T>()` 的隐式全局访问；若确需，必须在 `AppContext` 中集中登记并记录 ADR。
4. 禁止 `MonoSingleton<T>`、`Instance` 静态属性、`DontDestroyOnLoad` 魔法对象。

```csharp
// ✅ 组合根
public sealed class AppInstaller
{
    public AppContext Build(IConfigSource configSource)
    {
        var database  = new CardDatabase(configSource);
        var save      = new SaveService(new JsonFileStore(_paths));
        var collection= new CollectionService(save);
        var economy   = new EconomyService(save);
        var gacha     = new GachaService(database, economy, collection, new SeededRandomProvider());
        var ruleEngine= new RuleEngine(database);
        return new AppContext(database, collection, economy, gacha, ruleEngine);
    }
}
```

### 5.8 对象池规范

1. 所有"对局中高频创建/销毁"的对象必须走池：卡牌视图、伤害数字、箭头、特效。
2. 池对象必须有 `Reset()`/`OnSpawn()`/`OnDespawn()`，归还时清理状态。
3. 池必须有容量上限与超限策略（丢弃或扩容并打日志）。
4. 池化只针对**表现对象**；领域对象用结构/小对象，靠数量控制而非池化。

### 5.9 内核解耦与状态序列化规范（铁律 11，为服务端权威状态同步预留）

**适用范围：`0_Core`、`1_Domain`、`2_Application`。**
表现层（`4_Presentation`）不受限，可以自由使用 Unity API；但**表现层不得把结果回写给规则层**。

#### 5.9.1 五条禁令

| # | 禁令 | 原因 | 正确做法 |
| --- | --- | --- | --- |
| 1 | 禁止 `using UnityEngine` / `UnityEngine.*` 出现在这三层 | 服务器（Unity 工程外的 .NET 进程）要直接复用这份源码 | 只用 `System.*`；平台相关能力通过接口注入 |
| 2 | 禁止 `Debug.Log` / `UnityEngine.Mathf` / `Vector2` 等 Unity 类型 | 服务器进程里根本不存在这些类型 | 用 `GameLog`；数值/几何用 BCL 或自建类型 |
| 3 | 禁止 `JsonUtility` / `ScriptableObject` / `[SerializeField]` 参与状态序列化 | 服务器无法使用 Unity 的序列化 | 用 `System.Text.Json` / MessagePack / 自定义二进制，服务端与客户端共用同一实现 |
| 4 | 禁止直接调用 `DateTime.Now` / `UnityEngine.Time` / `UnityEngine.Random` | 环境依赖导致测试与服务端行为不可控 | 走 `IClock` / `IRandomProvider`（由外层注入） |
| 5 | 禁止在 `MatchState` 中持有 UI、`MonoBehaviour`、`GameObject`、`Transform` 等引用 | 无法序列化、无法裁剪、无法在服务器构造 | 状态只放可序列化的数据；引用用 Id / Key 表达 |

```csharp
// ❌ 违规：规则层依赖 Unity，服务器无法复用
using UnityEngine;
public void ApplyDamage(CardInstance target)
{
    Debug.Log("damage");                       // Unity 日志
    float crit = Random.value;                 // Unity 随机
    int dmg = Mathf.RoundToInt(baseDamage * crit);
    target.Health -= dmg;
    target.View.transform.localScale = ...;    // 状态里混入表现引用
}

// ✅ 正确：只用 BCL + 注入的环境依赖
public void ApplyDamage(CardInstance target, MatchContext ctx)
{
    var roll = ctx.Random.NextInt(0, 100);     // 注入的随机源
    var dmg = roll < ctx.Config.CritChance ? baseDamage * 2 : baseDamage;

    // 状态变更只是数据变化；表现由事件驱动（见 5.9.4）
    target.Health -= dmg;
    ctx.Emit(new DamageDealt(target.Id, dmg, target.Health));
}
```

> 说明：规则层**允许使用浮点数**（这是状态同步相对帧同步的一大优势）。仍建议在数值/百分比场景优先使用整数，
> 理由是便于测试断言与显示一致——但这属于 **P3 建议**，不是铁律，不会被门禁拦截。

#### 5.9.2 环境依赖注入

```csharp
public interface IClock
{
    /// <summary>逻辑时间：与真实时间解耦，便于测试与服务端推进。</summary>
    int CurrentTick { get; }
}

public interface IRandomProvider
{
    int NextInt(int minInclusive, int maxExclusive);
    void Shuffle<T>(IList<T> list);
}

public interface ILogSink          // GameLog 的后端，由外层注入
{
    void Write(LogLevel level, LogChannel channel, string message);
}
```

要求：

1. 规则层**只依赖接口**；`UnityEngine` 版本的实现放在 `Card.Infrastructure`，服务端版本放在 `Card.Server`。
2. 随机源由**服务器**（PVP）或本地对局（PVE）注入种子；测试可注入固定种子以获得可复现断言。
3. 洗牌算法固定（Fisher–Yates）并在注释中写明，便于测试与复盘。

#### 5.9.3 状态与事件的职责划分

| 概念 | 职责 | 是否下发网络 |
| --- | --- | --- |
| `MatchState` | 当前"是什么"（权威数据） | ✅ 作为快照 / 增量的数据来源（**裁剪后**） |
| `GameEvent` | "发生了什么"（因果，供表现与日志消费） | ✅ 随增量下发（也用于本地 PVE 表现） |
| 表现对象（`CardView` 等） | 渲染与动画 | ❌ |

规则：

1. **状态只存数据**，不含任何 UI / Unity 对象引用（用 Id / Key 引用）。
2. 事件在结算完成后按顺序**批量产出**，不在结算中途回调表现层。
3. 事件必须携带足够信息让表现层独立播动画（例如伤害事件带来源、目标、数值、剩余生命）。
4. 效果链（死亡 → 亡语 → 召唤 → 战吼）必须有**深度上限与访问集合**，避免无限循环；上限写进配置。

#### 5.9.4 状态序列化与增量

```csharp
public interface IMatchStateSerializer
{
    byte[] Serialize(MatchState state);            // 快照（服务端与客户端同一实现）
    MatchState Deserialize(byte[] payload);
}

public interface IStateDiffer
{
    /// <summary>计算 from → to 的变化列表，供服务器下发增量。</summary>
    IReadOnlyList<StateChange> Diff(MatchState from, MatchState to);
}
```

要求：

1. 序列化实现**放在 BCL 层**（`System.Text.Json` / MessagePack / 自定义二进制），不得使用 `JsonUtility`。
2. 序列化格式带 `schemaVersion`；字段遵循"只加不删、新增可选"演进原则。
3. 序列化往返必须语义一致，并有单测（含空状态、满场满手、多效果链等极端局面）。
4. 状态变更应尽量**局部化**（如"某随从生命 -3"），使增量体积小且易于裁剪。

| 类别 | 模式 |
| --- | --- |
| Unity 类型 | `using UnityEngine`、`UnityEngine.` 引用、`Vector2/3/4`、`Quaternion`、`Color`、`Rect` |
| Unity 日志 / 数值 | `Debug.Log*`、`Mathf.` |

| Unity 随机 / 时间 | `UnityEngine.Random`、Unity `Time.*`（`time`/`deltaTime`/`unscaledTime`/`realtimeSinceStartup`/`fixedTime`/`frameCount`） |

两条实现要求（M1-R3 的教训）：

> 完整设计见 [05-联网对战(状态同步)设计文档](./05-联网对战_状态同步_设计文档.md)。以下是**编码时必须遵守的约定**。

| 编号 | 规范 |
| --- | --- |
| N-1 | 网络与服务器代码只放在 `Card.Network` / `Card.Server`；`0_Core` / `1_Domain` / `2_Application` 不得出现任何网络类型 |
| N-2 | `Card.Presentation` 不引用 `Card.Network`；需要网络能力时依赖 `Card.Application` 中的接口（`IRoomService`、`IMatchSession`），实现由 Bootstrap 注入 |

| N-4 | **权威只在服务器**：客户端只上行 `GameCommand`，不得直接修改权威状态；客户端本地状态只用于显示与预测 |
| N-5 | 下行内容 = 服务器产出的状态快照 / 增量 + 事件；客户端不得自行推进对局结果 |
| N-6 | 任何来自客户端的数据都视为**不可信输入**：会话、序号、回合归属、字段范围、命令合法性、请求频率都要校验；非法数据只记录并拒绝，不崩溃 |
| N-7 | 协议消息带 `protocolVersion` 与长度前缀；版本不匹配时明确拒绝并提示，不尝试"猜" |
| N-8 | 网络异常（超时、断开、乱序、重复、版本冲突）必须可恢复（请求快照）或明确终止，禁止静默卡死；所有异常路径有日志 |
| N-9 | **视野裁剪单点实现**：`PlayerViewProjector` 是唯一裁剪入口；任何下发路径（含快照与重连数据）都必须经过它，禁止绕过 |
| N-10 | 网络层必须有统计：RTT、丢包、下行带宽、版本冲突次数、命令拒绝原因；可在开发面板查看并导出 |
| N-11 | 联网失败不影响 PVE：`Card.Network` 可被整体移除，项目仍能编译出包 |
| N-12 | **本阶段传输使用 BCL（`System.Net.Sockets`）+ 长度前缀消息，不引入任何第三方网络库**；未来引入必须走 ADR 并验证包体与启动开销 |
| N-13 | 客户端预测（若启用）只能驱动表现，不得写入本地权威状态；必须能在一次和解中完全撤销 |
| N-14 | 服务器必须以 `RuleEngine.Validate` 复用同一份规则，禁止在服务器侧另写一套简化校验 |
| N-15 | **权威运行时 `MatchHost` 只实现一份**（位于共享层），本地 / 房主 / 专用服务器三种宿主共用；禁止为房主模式或服务端各写一套权威逻辑 |
| N-16 | 宿主差异只允许出现在"传输、进程生命周期、部署配置"三处；任何涉及规则、校验、裁剪、快照的逻辑都不得按宿主分支 |
| N-17 | **本阶段只实现 `LocalHost` 与 `PeerHost`**，连接范围为回环与局域网；禁止在本阶段引入匹配服务、账号体系、NAT 穿透、中继、反作弊与客户端预测（列入阶段三） |

## 7. 异步与协程规范

1. **不加第三方异步库**（不引入 UniTask），统一用 `Coroutine` + 抽象接口。
2. 需要取消的操作必须可取消（`Coroutine` 句柄 + 显式 `StopCoroutine`，或 `CancellationTokenSource` 包装）。
3. 表现动画不阻塞逻辑；逻辑结算同步完成，表现异步播放。
4. 场景加载、资源加载等耗时操作必须有"加载中"状态与失败处理。
5. 禁止 `while(true)` 无退出条件的协程；AI 回合必须带步数/时间上限。

## 8. 日志规范

```csharp
public static class GameLog
```

## 9. 数据与存档规范

### 9.1 配置数据

1. 源表 Excel → 导入器 → 生成 JSON（运行时读取）+ SO（编辑器预览）。
2. 生成物**由工具产出，禁止手改**，文件头写明"生成文件，请勿手动编辑"。
3. 生成物包含 `schemaVersion`，与 `ConfigSchema.CurrentVersion` 比对，不匹配时警告并尝试迁移。
4. 配置加载失败必须有明确错误（哪个文件、哪一行、哪个字段）。

### 9.2 玩家存档

```json
{
  "schemaVersion": 1,
  "savedAtUtc": "2026-10-03T12:00:00Z",
  "economy": { "coins": 60, "dust": 120 },
  "collection": { "NEUTRAL_PANGO": 8, "MAGE_FIREBALL": 4 },
  "decks": [ { "name": "默认卡组", "cards": { "NEUTRAL_PANGO": 2 } } ],
  "progress": { "levelsCleared": ["L1"], "gachaPityCounter": 3 }
}
```

规则：

1. 路径：`Application.persistentDataPath/save.json`（**禁止 `Application.dataPath`**）。
2. **原子写入**：写 `save.json.tmp` → 校验可反序列化 → 替换 `save.json`；保留一份 `save.bak`。
3. 每次结构性变更提升 `schemaVersion`，并提供 `SaveMigrator`。
4. 读取失败时：尝试备份 → 再失败则提示用户并加载默认存档，**不得崩溃**。
5. 存档不含运行时状态（对局中的临时数据不落盘）。
6. 存档键使用**卡牌 Key**（稳定字符串），不使用 Id 或数组下标。

## 11. 健壮性与安全

1. 公共 API 入口一律 `Guard` 校验参数，失败返回 `Result` 而非抛异常（可预期的业务失败）。
2. 不可预期错误（配置缺失、存档损坏）在边界处捕获并降级，不让异常穿透到游戏循环。
3. 所有随机走 `IRandomProvider`，便于复现；抽卡与洗牌**必须可注入种子**。
4. 数值边界：费用/攻击/生命/金币均做上下限约束，禁止负值导致逻辑异常。
5. 防作弊不是本项目重点，但存档做基本混淆，避免直接文本编辑刷资源（P2）。

| `fix/<简述>` | 缺陷修复 |
| `docs/<简述>` | 文档变更 |
| `refactor/<简述>` | 重构（不改行为） |

### 12.2 提交信息（Conventional Commits）

```
<type>(<scope>): <描述> [<文档/需求编号>]

type: feat | fix | refactor | test | docs | chore | perf | build
scope: core | domain | app | infra | view | input | config | save | ai | docs
```

示例：

```
feat(domain): 实现攻击同时结算与圣盾消耗 [FR-5.5]

```

要求：**一次提交只做一件事**；提交必须可编译；禁止提交 `Library/`、`Temp/`、`Logs/`、`*.csproj`、`*.sln`。

```csharp
namespace Card.Domain.Effects
{
    /// <summary>对目标造成固定伤害。配置写法：DamageEffect:3</summary>
    [Serializable]
    public sealed class DamageEffectData : IEffectData
    {
        public int Amount { get; init; }
        public TargetRule Target { get; init; }
    }

    public sealed class DamageEffectExecutor : IEffectExecutor<DamageEffectData>
    {
        public void Execute(DamageEffectData data, EffectContext context)
        {
            foreach (var target in context.ResolveTargets(data.Target))
            {
                context.DealDamage(target, data.Amount);
            }
        }
    }
}
```

### 14.2 领域服务（无 Unity 依赖）

```csharp
namespace Card.Application.Match
{
    public sealed class RuleEngine
    {
        private readonly ICardDatabase _database;

        public RuleEngine(ICardDatabase database)
        {
            _database = Guard.NotNull(database, nameof(database));
        }

        public CommandResult Validate(IGameCommand command, MatchState state)
        {
            return command switch
            {
                PlayCardCommand c => ValidatePlayCard(c, state),
                AttackCommand c   => ValidateAttack(c, state),
                EndTurnCommand c  => ValidateEndTurn(c, state),
                _                 => CommandResult.Invalid(CommandError.UnknownCommand)
            };
        }
    }
}
```

### 14.3 表现视图（只读订阅）

```csharp
namespace Card.Presentation.Battle
{
    public sealed class ManaView : MonoBehaviour
    {
        [SerializeField] private TMP_Text _currentText;
        [SerializeField] private TMP_Text _maxText;

        private IEventBus _eventBus;
        private IDisposable _subscription;

        public void Initialize(IEventBus eventBus)
        {
            _eventBus = Guard.NotNull(eventBus, nameof(eventBus));
            _subscription = _eventBus.Subscribe<ManaChanged>(OnManaChanged);
        }

        private void OnDestroy() => _subscription?.Dispose();

        private void OnManaChanged(ManaChanged evt)
        {
            _currentText.SetText("{0}", evt.Current);
            _maxText.SetText("{0}", evt.Max);
        }
    }
}
```
