# 04 代码复盘 Review 规范

> 版本：1.0 ｜ 状态：基线（Baseline）
> 上游依据：[01-开发需求文档](./01-开发需求文档.md)、[02-开发计划步骤文档](./02-开发计划步骤文档.md)、[03-开发规范文档](./03-开发规范文档.md)
> 本文定义**怎么验收代码、怎么复盘、AI 生成代码如何自检**。没有通过本文评审的代码 = 未完成。

---

## 1. 目的与四条原则

| 原则 | 含义 |
| --- | --- |
| 对事不对人 | 评审针对代码与决策，不针对作者 |
| 证据优先 | 每条问题必须给出**文件、位置、可复核的现象**，禁止"感觉不对" |
| 分级驱动 | 只有 P0/P1 阻断合并；P2/P3 可排期，但必须登记 |
| 闭环 | 每个问题必须落到"已修复 / 已登记任务 / 明确不修（记录理由）"三态之一 |

### 1.1 评审要回答的四个问题

1. **对不对**：是否满足对应的 FR 与验收标准？
2. **稳不稳**：边界情况、异常路径是否被处理与测试？
3. **合不合规**：是否满足 `03` 的铁律与禁止清单？依赖方向是否被破坏？
4. **好不好改**：下一个功能加进来，需要改动多少既有代码？

## 2. 角色与职责

| 角色 | 职责 |
| --- | --- |
| 作者（人 / AI Agent） | 提交前完成自检（第 7 节）；提供变更说明、测试证据、影响范围 |
| 评审者（人 / AI Agent） | 按第 5、6 节 Checklist 逐项检查；按第 8 节输出结论 |
| 门禁执行者 | 运行 `Tools/check.ps1` 与里程碑验收，给出通过/不通过 |

> **AI Agent 同时是作者与第一评审者**：AI 提交前必须先"以评审者身份"审自己的代码，并附上自检结果。自检不通过的代码不允许提交评审。

---

## 3. 触发时机与粒度

| 时机 | 范围 | 要求 |
| --- | --- | --- |
| 单任务完成 | 1 张任务卡 | 自检 + 一次评审（可 AI 自审 + 人工抽查） |
| 合并到 `main` 前 | 本次全部改动 | 门禁必须全绿 |
| 里程碑结束 | 整个里程碑 | 完整评审 + 里程碑复盘（第 9 节） |
| 缺陷修复后 | 修复 diff | 复核 + 回归测试证据 |
| 架构变更（ADR） | 影响面 | 必须评审"依赖方向是否被破坏" |

## 4. 问题分级标准

| 级别 | 名称 | 判定 | 处理要求 |
| --- | --- | --- | --- |
| **P0** | 阻断 | 编译/测试失败；运行时崩溃；破坏铁律（依赖方向、Domain 引 UnityEngine、出包失败）；数据丢失或存档损坏风险；安全/兼容性问题 | **必须立即修复后才能合并** |
| **P1** | 严重 | 逻辑错误或与 FR/AC 不符；边界未处理（空牌库/满场/嘲讽）；无测试的关键路径；可复现的表现层写数据；性能明显不达标 | **必须修复后才能关闭任务**；无法当次修复需给出明确排期并由评审者确认 |
| **P2** | 一般 | 规范偏差（命名、结构、注释）；可维护性问题；重复代码；体验瑕疵 | 登记任务，可在里程碑内修复 |
| **P3** | 建议 | 优化建议、风格偏好、可选重构 | 记录，作者可拒绝并说明 |

> 判定原则：**"会不会导致用户可感知的错误或未来无法扩展"** 是 P0/P1 与 P2 的分界线。

## 5. 通用 Checklist（每次评审必查）

### A. 需求一致性

- [ ] 改动可追溯到具体 FR 编号与验收标准
- [ ] 需求的全部 AC 都被满足（逐条对照，不是"大概做了"）
- [ ] 明确"不做"的部分没有被顺手实现或被破坏
- [ ] 未引入 PRD 之外的行为（如改了概率、改了数值）

### B. 架构合规

- [ ] 依赖方向正确（没有反向引用）
- [ ] `0_Core` / `1_Domain` / `2_Application` 中没有 `using UnityEngine`、`Debug.Log`、`JsonUtility`、`Mathf`、`UnityEngine.Random`
- [ ] 没有新增 `Singleton` / `Instance` / `GameObject.Find` / `FindAnyObjectByType`
- [ ] 没有 `UnityEditor` / `AssetDatabase` 出现在运行时程序集
- [ ] View 中没有规则判断（`if (phase/canXxx)`）
- [ ] 新增玩法走"数据 + 效果组件"，没有新增继承层级
- [ ] 规则层状态可序列化、不含 UI / `MonoBehaviour` / `GameObject` 引用（铁律 11）
- [ ] 客户端没有直接修改权威状态的路径；所有变更可追溯到经服务器校验的命令（铁律 12）
- [ ] `Card.Presentation` 没有引用 `Card.Network`；下发的状态都经过视野裁剪（铁律 12）

### C. 正确性与边界

- [ ] 参数校验与失败路径明确（返回 `Result`，不是静默忽略）
- [ ] 边界场景被覆盖：0 / 负数 / 上限 / 空集合 / 重复操作
- [ ] 关键边界场景：空牌库（疲劳）、手牌满（爆牌）、场地满、无目标、费用不足、嘲讽
- [ ] 并发/顺序问题：多次触发同一效果、同回合多次操作不会重复结算
- [ ] 随机行为可注入种子

### D. 测试

- [ ] 新增/修改的逻辑有对应测试（Domain/Application 必测）
- [ ] 测试覆盖正常路径 + 失败路径 + 边界
- [ ] 测试命名符合 `方法名_场景_期望结果`
- [ ] 测试不依赖执行顺序、不依赖真实时间、可重复运行
- [ ] 覆盖率达到或高于当前基线

### E. 可维护性

- [ ] 单文件 ≤ 300 行、单方法 ≤ 50 行、圈复杂度 ≤ 15
- [ ] 命名符合规范；无拼音、无无意义缩写
- [ ] 无重复逻辑（同一规则只在一个地方实现）
- [ ] 注释解释"为什么"，公共 API 有 XML 注释
- [ ] 无死代码、无注释掉的大段代码

### F. 性能与内存

- [ ] 热路径无每帧分配（无 LINQ/闭包/字符串拼接）
- [ ] 高频对象走对象池，没有对局中 `Instantiate/Destroy` 卡牌
- [ ] `GetComponent` 不在 `Update` 中调用
- [ ] 无明显 N+1 或全表遍历

### G. 日志与可观测

- [ ] 使用 `GameLog` 且带通道，无 `Debug.Log`
- [ ] 错误日志包含定位信息（卡牌 Key / 玩家 Id / 命令类型）
- [ ] 关键流程有可追踪的事件输出

### H. 文档与配置

- [ ] 涉及需求/计划/规范的改动同步更新了 `Docs/`
- [ ] 新增配置项已在 Excel 与导出数据中体现，并有校验
- [ ] 提交信息符合 Conventional Commits 且引用了需求编号

## 6. 分层专项 Checklist

### 6.1 Domain / Application（规则层）

- [ ] 纯 C#，零 Unity 依赖，可在 EditMode 测试中直接构造
- [ ] 状态修改只通过 `RuleEngine.Apply` / 领域方法，外部不能直接改字段
- [ ] 所有随机通过 `IRandomProvider`
- [ ] 命令不可变；校验与结算分离（`Validate` 不改状态）
- [ ] 事件在结算完成后统一发布，发布的是"已发生的事实"

### 6.2 Infrastructure（服务层）

- [ ] 外部 I/O（文件、网络）有失败处理与降级
- [ ] 存档：原子写入 + 版本号 + 迁移 + 损坏兜底
- [ ] 配置：加载失败给出精确错误位置，不产生半成品数据
- [ ] 时间/随机/路径等环境依赖通过接口注入，便于测试

### 6.3 Presentation（表现层）

- [ ] 只读订阅，绝不修改游戏状态
- [ ] 订阅在 `OnEnable`/`Initialize` 建立、`OnDisable`/`OnDestroy` 解绑（无泄漏）
- [ ] 使用 TMP，不使用 Legacy `Text`
- [ ] 分辨率变化后布局与指向箭头仍正确
- [ ] 动画不阻塞逻辑；可被设置项加速/关闭

### 6.4 Input / Controller

- [ ] 只产出 `GameCommand`，不做合法性判断
- [ ] 非法操作有明确用户反馈（而非静默无响应）
- [ ] 指向模式可取消（右键 / Esc），不会卡在中间态
- [ ] 输入不直接读 `Input.*`（走 `IInputSource`）

### 6.5 Editor 工具

- [ ] 仅位于 `Card.Editor` 程序集
- [ ] 导入前校验，失败时中止且不写入半成品数据
- [ ] 生成的资源带"请勿手改"标识与版本号
- [ ] 工具操作可重复执行（幂等）

### 6.6 内核解耦 / 服务器权威专项（阶段一即强制，阶段二重点）

**内核解耦与可序列化（每次触及规则层都要查）**

- [ ] `0_Core` / `1_Domain` / `2_Application` 中无 `using UnityEngine`、无 `UnityEngine.*` 类型
- [ ] 无 `Debug.Log` / `Mathf` / `Vector2` / `Time` / `UnityEngine.Random` / `JsonUtility` / `ScriptableObject`
- [ ] 时间走 `IClock`、随机走 `IRandomProvider`、日志走 `GameLog`（均可注入、可测试）
- [ ] `MatchState` 中不含 UI / `MonoBehaviour` / `GameObject` / `Transform` 引用
- [ ] `MatchState` 序列化往返一致（附测试名与证据），且不依赖 Unity 序列化
- [ ] 状态可计算增量（`StateChange`），无变更时产出空增量
- [ ] 状态变更统一产出 `GameEvent`，事件顺序与结算顺序一致
- [ ] `Card.Server` 能编译并通过"无 Unity 环境跑完整对局"的测试

**服务器权威与状态同步（阶段二）**

- [ ] 网络与服务器代码仅在 `Card.Network` / `Card.Server`；规则三层无网络类型
- [ ] 客户端不直接修改权威状态，所有变更可追溯到一条经服务器校验的命令
- [ ] 服务器侧命令校验齐全：会话、序号幂等、回合归属、`RuleEngine.Validate`、频率限制
- [ ] 下行只有"状态快照/增量 + 事件"，客户端不自行推进对局结果
- [ ] 所有下发路径（含快照与重连数据）都经过 `PlayerViewProjector` 裁剪
- [ ] 有自动化断言：任一下发数据不含对手手牌明细与牌库顺序
- [ ] 入站数据全量校验（长度/范围/序号/版本），非法即拒绝且不崩溃
- [ ] 消息带 `protocolVersion`；版本不匹配被明确拒绝
- [ ] 异常路径（超时/断开/乱序/重复/版本冲突/服务器异常）都有明确终态与日志
- [ ] 客户端预测（若启用）只驱动表现、可完全撤销、不写入本地权威状态
- [ ] 移除 `Card.Network` 后项目仍可编译出包；服务器不可用时 PVE 正常
- [ ] **阶段范围锁（阶段二）**：只实现 `LocalHost` + `PeerHost`；未引入第三方网络库；未实现匹配 / 账号 / NAT 穿透 / 中继 / 客户端预测（这些属阶段三）
- [ ] **本机双进程可验证**：构建可用启动参数区分房主与加入方，`127.0.0.1` 直连可跑通

## 7. AI 生成代码的自检流程（提交前必做）

### 7.1 六步自检

```
第 1 步：需求对齐
  - 逐条列出本次对应的 FR/AC，逐条标注"已满足 / 未满足 / 不涉及"
第 2 步：铁律扫描
  - 对照 Docs/03 第 1 节与第 13 节禁止清单，逐项自查，输出"命中/未命中"
第 3 步：边界推演
  - 主动列出 ≥ 5 个边界场景，说明每个场景下的行为与是否有测试
第 4 步：测试证据
  - 给出实际运行结果（通过数量、覆盖的关键分支），不得只说"已测试"
第 5 步：影响面评估
  - 说明改动影响了哪些既有模块、是否需要同步改文档/配置、是否有回归风险
第 6 步：反向审查
  - 以"挑刺者"身份提出 ≥ 3 条可能的问题，并说明为何不成立或已修复
```

### 7.2 自检提示词模板（可直接复制给 AI）

```
请以严格评审者身份审查你刚刚完成的改动，不要复述代码功能，只输出以下内容：

1. 需求对齐表：| AC 编号 | 是否满足 | 证据（文件:行 / 测试名） |
2. 铁律自查表：逐条列出 Docs/03 的 13 条铁律与禁止清单命中情况
3. 边界场景表：| 场景 | 期望行为 | 实际行为 | 对应测试 |
   必须包含：空集合、上限、负数、重复操作、非法状态
4. 测试证据：实际运行的测试类与用例名、通过数量、覆盖的分支
5. 影响面：受影响的模块、需要同步更新的文档或配置、回归风险点
6. 反向审查：你认为最可能被挑出的 3 个问题及你的处理结论
7. 结论：是否达到可提交标准（是/否），未达标项列出

要求：任何"已验证"的结论都必须附可复核证据；无法提供证据的，明确标注"未验证"。
```

### 7.3 AI 常见"假达标"信号（出现即视为未完成）

| 信号 | 说明 |
| --- | --- |
| "已实现"但没有测试 | 无证据的完成声明 |
| 只测正常路径 | 边界与失败路径缺失 |
| 测试里只写 `Assert.IsNotNull(result)` | 断言过弱，等于没测 |
| 改测试让它通过（降低断言、跳过用例） | 掩盖问题，P0 |
| 用 `try/catch` 吞掉异常 | 掩盖失败路径 |
| 用 `#if UNITY_EDITOR` 绕过运行时限制 | 依然是运行时污染，P0 |
| 只在编辑器里手点验证 | 未覆盖出包与边界，需补自动化测试 |
| 大改无关文件 | 变更范围失控，需拆分 |

### 9.1 5 Why 使用要求

1. 只对 **P0/P1 缺陷** 与 **工期偏差 > 30%** 的问题做 5 Why。
2. 根因必须落到**可改进的机制**上，不允许停在"粗心""时间不够"。
3. 每条根因必须对应至少一个改进任务，否则复盘无效。

## 10. 质量度量指标

| 指标 | 定义 | 目标 | 采集方式 |
| --- | --- | --- | --- |
| 缺陷密度 | P0+P1 数 / 千行新增代码 | ≤ 2 | 评审记录统计 |
| P0 缺陷 | 阻断级缺陷数 | 0 | 评审记录 |
| 返工率 | 因评审不通过被退回的任务数 / 总任务数 | ≤ 10% | 任务卡状态 |
| 测试覆盖率 | Domain+Application 行覆盖率 | ≥ 80% | 覆盖率报告 |
| 门禁通过率 | 一次通过门禁的任务数占比 | ≥ 80% | check.ps1 记录 |
| 编译警告 | 编译警告数量 | 0 | 构建日志 |
| 架构违规数 | 违反铁律的次数 | 0 | 评审记录 |
| 单文件超限 | 超过 300 行的文件数 | 0 | check.ps1 |
| 平衡偏差 | 卡组胜率偏离 50% 的幅度 | ≤ 5% | AI 模拟报告 |
| 平均对局回合数 | AI vs AI 平均回合 | 8–12 | AI 模拟报告 |
| 内核解耦违规数 | `0_Core`/`1_Domain`/`2_Application` 中出现 Unity 依赖的处数 | 0 | check.ps1 + `Card.Server` 编译 |
| 状态序列化测试 | 序列化往返测试通过率 | 100% | 测试报告 |
| 权威性违规数 | 客户端可影响对局结果的路径数 | 0 | 评审 + 作弊注入测试 |
| 视野裁剪测试 | 隐藏信息断言通过率 | 100%（失败即 P0） | 服务器侧测试 |

| 重连成功率（阶段二） | 重连窗口内成功恢复的比例 | ≥ 95% | 网络日志统计 |
| 客户端预测纠正率（阶段二，若启用） | 预测被推翻的比例 | ≤ 30%（超出则关闭预测） | 客户端统计 |

## 11. 门禁与不通过处理

### 11.1 门禁清单（与 `02` 第 5 节一致）

### 11.2 不通过处理流程

```

  → 登记（含位置与建议），进入里程碑待办池
```

## 12. 常见缺陷案例库（取自旧项目真实问题）

> 用于评审时对照，识别"同类问题是否再次出现"。

### 案例 1：运行时代码引用编辑器 API（P0）

**现象**：`BattleManager.cs` 第 3 行 `using UnityEditor;`；`PlayerData.cs` 第 5、80 行使用 `AssetDatabase.Refresh()`。
**后果**：独立包编译失败；编辑器内一切正常，出包才暴露。
**教训**：编辑器能力必须放进 Editor 程序集；`check.ps1` 必须自动扫描。
**对应规范**：铁律 7、U-1。

### 案例 2：索引当 ID 用（P0）

**现象**：`CardStore.CopyCard(_id)` 直接 `cardList[_id]`；`DeckManager` 也按数组下标取卡。
**后果**：一旦配置表行序变化或出现空行，全部卡牌错位，且不报错。
**教训**：一律用 id/key 字典查询；禁止 `list[index]` 当业务 ID。
**对应规范**：PRD 7.3 第 4 条、禁止清单。

### 案例 3：洗牌参数与牌组索引不一致（P1）

**现象**：`GameStart()` 调用 `ShuffletDeck(0)` / `ShuffletDeck(1)`，而方法内部判定 `_player == 1` / `== 2`。
**后果**：玩家 1 从不洗牌；玩家 2 顺序固定，游戏体验与测试都失真。
**教训**：玩家索引必须全局统一（0/1 或 1/2），并写测试锁定。
**对应规范**：铁律 9（必须有测试）。

### 案例 4：表现层直接修改游戏数据（P1）

**现象**：`AttackTarget.ApplyDamage()` 直接 `enemy.HP -= _damage` 并在 ≤0 时 `Destroy(gameObject)`。
**后果**：规则散落在 UI 组件里；无法在没有 UI 的环境验证；死亡结算绕过所有管线（亡语、坟场、胜负）。
**教训**：表现层只读；伤害与死亡必须走统一结算管线。
**对应规范**：铁律 4、5.6。

### 案例 5：全局单例 + 硬查找耦合（P1）

**现象**：`BattleManager.Instance` 被交互组件广泛调用；`ClickCard` 用 `GameObject.Find("DeckManager")`。
**后果**：无法单元测试、无法多实例（AI 模拟跑多局会串数据）、改名即崩溃。
**教训**：组合根注入 + 接口依赖。
**对应规范**：铁律 8、5.7。

### 案例 6：空集合未判空（P0）

**现象**：`DrawCard` 第 221 行 `drawDeck[0]`，无长度检查。
**后果**：牌库抽干抛异常，对局中断。
**教训**：所有集合访问都要考虑空；规则层要有疲劳等明确定义的兜底行为。
**对应规范**：第 5 节 C 组边界检查。

### 案例 7：字符串拼接式手写解析且无校验（P1）

**现象**：`CardStore.LoadCardData` 用 `Split('\n')` / `Split(',')`，注释判断只检查首列，空行会越界。
**后果**：配置多一个空行就崩；无法定位是哪个文件哪一行出错。
**教训**：导入必须结构化 + 全字段校验 + 精确报错。
**对应规范**：PRD FR-1.2、6.5。

### 案例 8：分辨率快照导致表现错误（P2）

**现象**：`Arrow.cs` 的 `screenWidth/screenHeight` 在字段初始化时取一次，窗口缩放后箭头长度/位置错误。
**后果**：非全屏或改分辨率时 UI 明显错位。
**教训**：屏幕相关计算每帧取值或用 `RectTransformUtility` 换算。
**对应规范**：U-7、U-8。

### 案例 9：规则层与 Unity 耦合，服务器无法复用内核（P0，前瞻性防范）

**现象**：在规则层写 `Debug.Log`、用 `UnityEngine.Random` 决定暴击、用 `JsonUtility` 序列化对局状态、把 `CardView` 引用放进 `MatchState`。
**后果**：服务端无法编译同一份代码，只能复制一份"服务器版规则"，从此双份维护、长期不一致；状态也无法裁剪与下发。
**教训**：状态同步方案下，**规则代码必须能在无 Unity 的进程里编译运行**。这个边界在阶段一就要守住，不能留到阶段二"改造"。此类违规按 P0 处理，不因"现在只是单机"而降级。
**对应规范**：铁律 11、5.9。

### 案例 10：客户端直接改状态，或服务器信任客户端上报（P0）

**现象**：客户端本地结算后把结果上报服务器；或客户端把"我的生命值是 30"这类状态发给服务器，服务器直接采用。
**后果**：改内存或改包即可作弊；对局结果不可信；也无法追溯"谁改了什么"。
**教训**：客户端只能上报**意图**（`GameCommand`），状态永远由服务器计算；所有入站数据都按不可信输入校验。
**对应规范**：铁律 12、N-4、N-6。

### 案例 11：视野裁剪写在多处，遗漏一处即泄露手牌（P0）

**现象**：为图方便，在"广播状态"、"重连补发快照"、"观战数据"三处各写一遍裁剪逻辑。
**后果**：任意一处漏掉，对手手牌就会随包下发，抓包即可看到，属严重安全缺陷。
**教训**：裁剪必须**单点实现**（`PlayerViewProjector`），所有下发路径强制经过它，并配自动化断言。
**对应规范**：N-9、N-5。
