## 2. 现有模块解构

按"职责"重新切分旧代码，得到 9 个事实上的模块。**注意：旧代码并没有按模块分文件，一个类往往横跨多个职责。**

### M1 配置数据模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `CardStore`（88 行）、`Cardlist.csv` |
| 做什么 | `LoadCardData()` 按行 `Split('\n')`、按列 `Split(',')`，用首列字符串 `enemy` / `magic` 决定 new 哪个子类 |
| 数据结构 | `List<Card> cardList`，**下标 == 卡牌 Id** |
| 问题 | 手写 CSV 解析无转义、无容错；`cardList[_id]` 假设"CSV 行序 == id 序"；`#` 注释行仅跳过首列，空行会 `IndexOutOfRange`；无字段校验；无版本/无 schema；新增字段必须改代码 |

### M2 卡牌模型模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `Card` / `EnemyCard` / `MagicCard`（`Card.cs`，40 行，一文件三类） |
| 做什么 | 用**继承**表达卡牌种类：随从卡有 attack/HP/HPMAX/attackTime，法术卡有 effect(string) |
| 问题 | 典型"继承表达玩法"：新增"武器卡""英雄卡"要改基类与所有 `is` 判断；`MagicCard.effect` 是**永不执行的字符串**；`CopyCard()` 手工逐个字段拷贝，新增字段必漏；`Card` 是可变运行时对象，没有"配置定义 / 对局实例"分离 |

### M3 玩家数据模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `PlayerData`（82 行） |
| 做什么 | `int[] playerCards` / `int[] playerDeck` / `playerCoins`；`LoadPlayerData()` 读 CSV；`SavePlayerData()` **写回 `Application.dataPath + "/Data/Playerdata.csv"` 并调用 `AssetDatabase.Refresh()`** |
| 问题 | 🔴 **P0**：`using UnityEditor;`（第 5 行）与 `AssetDatabase`（第 80 行）出现在运行时脚本 → **打包必然编译失败**；`Application.dataPath` 在真机/发布版是只读路径；存档写在工程源目录里，会污染版本库；数组长度依赖 `cardStore.cardList.Count`，加载顺序耦合 |

### M4 抽卡（开包）模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `OpenPackage`（67 行） |
| 做什么 | 判定金币 ≥10 → 扣费 → 清空临时池 → `cardStore.RandomCard()` 抽 5 张 → 累加 `playerCards[id]` → 存盘 |
| 问题 | `Random.Range` 等概率抽取，**无稀有度权重、无保底、无重复处理**；金币与卡池硬编码在同一方法；抽卡结果无动画/无揭示流程；`SaveCardData()` 遍历 GameObject 反查数据，把表现对象当数据源 |

### M5 卡组编辑模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `DeckManager`（126 行）+ `ClickCard` + `CardCount` + `LibraryCard/DeckCard` 预制体 |
| 做什么 | 两个 `Dictionary<int,GameObject>` 缓存 UI 项，点击在"仓库↔卡组"间移动一张，实时改 `playerCards[] / playerDeck[]` |
| 问题 | `ClickCard` 用 `GameObject.Find("DeckManager")` 硬找对象（第 17 行），对象改名即崩；数量为 0 时用 `Destroy(gameObject)` 让 UI 自己消失，逻辑与表现混在一起；**无卡组合法性校验**（张数、同名上限、职业限定）；UI 与数据双向硬耦合，无法做"未保存的编辑态" |

### M6 对战流程模块（核心，也是最需要重做的部分）

| 项 | 内容 |
| --- | --- |
| 承载类 | `BattleManager`（409 行，`MonoSingleton`）+ `GamePhase` 枚举 |
| 职责清单 | 玩家数据持有、卡组加载、洗牌、抽牌、回合切换、阶段显示刷新、召唤校验、召唤执行、攻击校验、攻击执行、伤害结算、箭头特效创建/销毁、备战区高亮开关、鼠标右键取消 —— **14 项职责** |
| 阶段 | `gameStart → player1Draw → player1Action → player2Draw → player2Action → …` |
| 问题 | 上帝对象；状态机是散落在 6 个 `if (gamePhase == …)` 中的散装逻辑，无显式状态类；**无费用/法力水晶系统**（只有 `SummonCountMax` 召唤次数）；**无胜负判定**（打不出"一局"）；攻击是单向的（`Attack()` 只结算攻击方，防御方不反击、不结算英雄）；无嘲讽/冲锋/召唤失调等关键词；无疲劳；`DrawCard` 不判空牌库 |

### M7 表现层模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `CardDisplay`（47 行）、`ZoomUI`、`CardCount`、`Arrow` |
| 做什么 | `CardDisplay` 直接持有 `Card` 数据并写 `Text.text`；`Arrow` 每帧用 `Input.mousePosition` 重算箭头长度/角度 |
| 问题 | 表现类**持有并修改数据**（`AttackTarget.ApplyDamage` 直接改 `EnemyCard.HP`）；用 Legacy `Text` 而非 TMP；`Arrow.screenWidth/screenHeight` 是**构造时快照**，窗口缩放后箭头位置错误；`ZoomUI` 直接改 `localScale`，不还原布局 |

### M8 交互模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `BattleCard`、`AttackTarget`、`Block`（均实现 `IPointerDownHandler`） |
| 做什么 | 各自在 `OnPointerDown` 里判断 `BattleManager.Instance.gamePhase`，再反向调用 BattleManager 的方法 |
| 问题 | 交互组件**知道规则细节**（如"`attackable` 且当前是自己回合"），规则散落在 UI 组件里；`AttackTarget.ApplyDamage` 直接 `Destroy(gameObject)`，绕过任何死亡结算管线；`Block.card` 因此持有已销毁对象（依赖 Unity 伪 null 侥幸不崩） |

### M9 基础设施模块

| 项 | 内容 |
| --- | --- |
| 承载类 | `MonoSingleton<T>`（27 行） |
| 问题 | 三重缺陷：① `BattleManager` 自己又声明了 `public static BattleManager Instance`（第 16 行）与基类 `Instance` **命名冲突/遮蔽**；② 基类 `Awake()` 被派生类 `private void Awake()` 遮蔽，单例赋值实际来自派生类；③ `instance = FindAnyObjectByType<T>()` 从未回写到静态字段；无 `DontDestroyOnLoad`、无线程安全、无重复实例策略一致性 |

## 3. 缺陷清单（按严重度）

> 每条都给了可复核的**证据位置**。这是重做时的"避坑检查表"。

### P0 — 阻断级（不修就无法交付）

| 编号 | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| P0-1 | 运行时代码引用编辑器 API | `BattleManager.cs:3` `using UnityEditor;`；`PlayerData.cs:5,80` `using UnityEditor;` + `AssetDatabase.Refresh()` | 无法出包；真机启动即崩 |
| P0-2 | 存档写入工程源目录 | `PlayerData.cs:58` `Application.dataPath + "/Data/Playerdata.csv"` | 发布版只读 → 存档失败；且污染版本库 |
| P0-3 | 洗牌参数与牌组索引不匹配 | `BattleManager.cs:161,165` 判定 `_player==1 / ==2`，而 `GameStart()` 调用 `ShuffletDeck(0)` / `ShuffletDeck(1)` | 玩家 1（索引 0）**从不洗牌**，玩家 2 永远抽到固定顺序；`ShuffletDeck(1)` 误洗 player1 牌组 |
| P0-4 | 抽牌不判空牌库 | `BattleManager.cs:221` `drawDeck[0]` 无长度检查 | 牌库抽干 → `IndexOutOfRangeException`，对局中断 |
| P0-5 | 无胜负判定 | 全工程无英雄血量、无胜负分支 | **不存在"完整可玩的一局"**，无法验收"完整跑通对战" |
| P0-6 | 无法力/费用系统 | 仅有 `SummonCountMax` / `SummonCounter`（`BattleManager.cs:41-42`） | 缺失卡牌游戏最核心的资源曲线，卡牌无"费用"字段，玩法不成立 |
| P0-7 | 战斗为单向伤害 | `Attack()` 只调 `_target.ApplyDamage(enemy.attack)` | 防御方不反击、不结算英雄生命；与《炉石传说》规则不符 |

### 4.2 目录与程序集结构

> 注（M2-T5）：`CardDatabase` 拆成两部分——**纯查询** `Card.Domain.Config.CardDatabase`（无 I/O、无 Unity，内核与 M11 服务端共用）
> 与**读盘** `Card.Infrastructure.Config.ConfigFileLoader`。这样"查询规则"能进无 Unity 的测试工具链，而文件 I/O 留在 Infrastructure。

```
Assets/
├─ _Project/                       ← 全部新代码放这里，与第三方资产隔离
│  ├─ 0_Core/                      Card.Core          （无依赖）
│  ├─ 1_Domain/                    Card.Domain        （→ Core）
│  ├─ 2_Application/               Card.Application   （→ Core, Domain）
│  ├─ 2_Network/                   Card.Network       （→ Core, Domain, Application）
│  ├─ 3_Infrastructure/            Card.Infrastructure（→ Core, Domain, Application）
│  ├─ 4_Presentation/              Card.Presentation  （→ 上述 + UnityEngine）
│  ├─ 5_Bootstrap/                 Card.Bootstrap     （→ 全部，Composition Root）
│  ├─ 6_Editor/                    Card.Editor        （Editor Only：Excel 导入、校验工具）
│  ├─ 7_Tests/
│  │  ├─ EditMode/                 Card.Tests.EditMode
│  │  └─ PlayMode/                 Card.Tests.PlayMode
│  ├─ Art/          （Sprite / UI / Font）
│  ├─ Audio/
│  ├─ Config/       （Excel 源表 + 导出的 SO/JSON）
│  ├─ Prefabs/
│  └─ Scenes/
└─ ThirdParty/  CartoonUI、TextMesh Pro（保持不动）
```

服务端（**Unity 工程之外**，共享同一份规则源码）：

```
Server/
├─ Card.Server/                   （未来）专用服务器宿主外壳；本阶段不建立
│  └─ Card.Server.csproj          以源码通配符方式编译 Assets/_Project/{0_Core,1_Domain,2_Application}
└─ Card.Server.Tests/             （未来）服务器侧测试
```

> 权威运行时（`MatchHost`、`RuleEngine`、`PlayerViewProjector`、快照/增量）位于 `2_Application` 共享层，
> **不在** `Server/` 里。这样房主模式（客户端进程内跑 `MatchHost`）与专用服务器可以复用同一份实现（ADR-15/16）。
> **本阶段不建立 `Server/` 目录**，只保留规划——避免"为了一个用不上的服务器先搭一堆工程"。

程序集引用矩阵（`asmdef`）：

| 程序集 | 可引用 |
| --- | --- |
| `Card.Core` | （无） |
| `Card.Domain` | Core |
| `Card.Application` | Core, Domain |
| `Card.Network` | Core, Domain, Application（**禁止被 Presentation 引用**） |
| `Card.Infrastructure` | Core, Domain, Application |
| `Card.Presentation` | Core, Domain, Application, Infrastructure, UnityEngine.UI/TMP |
| `Card.Bootstrap` | 全部 |
| `Card.Editor` | 全部 + UnityEditor（**仅此程序集与 Tests 可用 UnityEditor**） |
| `Card.Tests.*` | 被测程序集 + NUnit |
| `Card.Server`（Unity 工程外） | Core, Domain, Application（**不得引用任何 Unity 程序集**） |

> 用 `asmdef` 把"禁止反向依赖"变成**编译期错误**，而不是靠自觉。
> `Card.Network` 独立成程序集的目的是：**PVE 出包时可以直接不编译它**（NFR-14），联网功能因此是真正可插拔的。
> `Card.Server`（**未来**）是 Unity 工程之外的 .NET 程序，通过源码共享直接编译 `0_Core` / `1_Domain` / `2_Application`，
> 因此这三层**只允许依赖 BCL**——这一条把"服务器能复用规则代码"变成了编译期约束。

### 4.3 对局数据流

```
玩家点击/拖拽
   → PlayerInputController 产出 GameCommand（如 PlayCardCommand{handIndex, targetRef}）
   → CommandQueue 入队（保证顺序、可回放、可被 AI 复用）
   → MatchController 取出一条，交给 RuleEngine.Validate
        ├─ 非法 → 返回 CommandResult.Invalid(reason) → UI 提示，状态不变
        └─ 合法 → RuleEngine.Apply
              → 修改 MatchState（扣费 / 移区 / 结算伤害 / 判定死亡）
              → 收集 GameEvent 列表（CardPlayed / DamageDealt / MinionDied / ManaChanged …）
              → 触发 Trigger 链（战吼 / 亡语 / 回合开始结束）
              → 判定胜负
   → EventBus 批量发布事件
   → 各 View 订阅并播放表现（动画、音效、数字跳变）
   → View 只读 MatchState，绝不写
```

### 4.4 关键设计决策（ADR 摘要）

| 编号 | 决策 | 理由 | 被否方案 |
| --- | --- | --- | --- |
| ADR-01 | 效果用"数据组件 + 执行器"，不用继承 | 组合优于继承；新增卡牌只配数据 | `FireballCard : Card` |
| ADR-02 | 领域层纯 C#，零 `UnityEngine` | 规则可秒级单测、可脱离 Unity 跑回归 | 逻辑写在 MonoBehaviour |
| ADR-03 | 配置源支持 Excel → JSON/SO 双通道 | 策划用 Excel；运行时读 JSON 便于热更与校验 | 只用 ScriptableObject 手点 |
| ADR-04 | Definition（只读配置）与 Instance（对局状态）分离 | 一张卡可有多份带不同状态的对局实例 | 直接用 SO 存 HP |
| ADR-05 | 所有玩家输入走命令队列 | 人类与 AI 共用一条通路，天然支持回放/回退/录像 | 直接调方法 |
| ADR-06 | 事件总线解耦逻辑与表现 | View 可插拔；逻辑发布即可，不关心谁在看 | View 直接引用 Manager |
| ADR-07 | 组合根显式装配，禁用隐式全局单例 | 可测试、可多套实例（如 AI 模拟跑 1000 局） | `MonoSingleton.Instance` 满天飞 |
| ADR-08 | 存档用 JSON + 版本号 + 原子写入 | 跨平台可写、可迁移、不易损坏 | 写回 Assets 下 CSV |
| ADR-09 | 卡牌 UI 用对象池 | 对局高频洗牌/出牌，避免 GC 抖动 | 每次 Instantiate/Destroy |
| ADR-10 | 随机数走 `IRandomProvider` 接口，可注入种子 | 平衡性测试可复现；抽卡可审计 | 直接 `Random.Range` |
| ADR-11 | **`Card.Core` / `Card.Domain` / `Card.Application` 只依赖 BCL，零 `UnityEngine`** | 服务器要直接复用同一份规则代码（源码共享编译），且核心可脱离 Unity 单测 | 规则代码依赖 MonoBehaviour/JsonUtility（旧项目做法，服务器无法复用） |
| ADR-12 | **联网对战采用服务端权威 + 状态同步**：客户端上行命令，服务器下行状态与事件 | 隐藏信息（手牌）由服务器裁剪，天然安全；反作弊为中—高；回合制对延迟不敏感 | 确定性锁步帧同步（每个客户端都要算全局状态，隐藏信息只能靠客户端遮蔽） |
| ADR-13 | **网络层独立为可移除的 `Card.Network` 程序集**，其对外接口定义在 `Card.Application` | PVE 出包不依赖网络；表现层只面向接口，便于单独测试与降级 | 网络代码混入 Application/Presentation |
| ADR-14 | **状态必须可序列化、可裁剪、可增量**；状态变更统一产出 `GameEvent` | 快照（重连/首次进入）、增量下发、视野裁剪、表现驱动都依赖它 | 状态对象散落 UI 引用、只能整体发送（无法裁剪、无法增量） |
| ADR-15 | **权威运行时 `MatchHost` 是共享库（在 `Card.Application`），不是服务端专属代码** | 同一份权威实现可跑在三种宿主：本地（PVE）、房主客户端（`PeerHost`）、独立服务端（`DedicatedHost`），部署形态成为配置而非重写 | 把权威逻辑写进服务端工程（房主模式无法复用，必然出现第二套规则） |
| ADR-16 | **联网验证阶段只做房主模式（监听服务器），在单台 PC 上用两个进程验证**；专用服务器推迟到未来（仅保留 `IMatchHost` 接口与目录规划） | 零服务器成本、零运维、零新增网络依赖（BCL TCP 即可），可以最快验证"权威 + 状态同步"链路是否正确；`MatchHost` 共享保证将来切专用服务器是配置级改动 | 先上专用服务器（成本前置、迟迟打不通 PVP）；不做房主模式而直接等公网方案 |
| ADR-17 | **本阶段传输不引入第三方网络库**，使用 BCL `System.Net.Sockets` + 长度前缀消息 | 回环/局域网场景下 TCP 已足够可靠有序；省去包体、版本适配与 ADR 成本，把精力集中在同步正确性上 | 直接引入 Unity Transport / Photon（本阶段用不上其能力，却要承担依赖与包体） |
| ADR-18 | **规则内核的测试与覆盖率用"Unity 工程外的 .NET 工具链"度量**（`Tools/Coverage`，仅开发期；内核源码以链接方式复用，不复制） | ① M1 门禁要求 `Card.Core` 覆盖率 ≥ 90%，而 Unity 官方覆盖率包需要额外包依赖与联网拉取；② 内核在无 Unity 进程中编译并通过全部测试，本身就是 FR-13.2/13.3 的证据（M11 的服务器测试工程由此起步）；③ 不改动 `Assets/` 与 `Packages/`，对运行时零影响 | 只用 Unity 内覆盖率（受包依赖与联网限制）；或把内核源码复制一份到工具工程（必然与 UnityEngine 版本漂移） |
| ADR-19 | **配置源表用 CSV（`.csv`）而不是 `.xlsx`**：Excel/WPS/VSCode 都能直接打开与另存；导入器只需 BCL，零新增依赖 | 省掉第三方表格库（NPOI/EPPlus 之类）的依赖、联网拉包与版本维护；纯文本便于 git diff 与代码评审；代价是没有单元格下拉校验与多 Sheet 说明，改由 `Config/README.md` 承担说明职责 | 用 `.xlsx` + 第三方库（新增依赖与兼容风险），或让策划直接手改生成物（违反"生成物禁止手改"） |
| ADR-20 | **配置生成物只做 JSON；`ScriptableObject` 预览资产推迟**（M2-T3 范围调整） | ① Unity 序列化不支持 `init` 属性，做 SO 预览就得再写一套镜像模型，等于两份 schema 必然漂移；② 运行时真相只能有一个，JSON 已经满足"导表 → 运行"；③ SO 的唯一价值是 Inspector 里人工预览，等 M5 真正需要时再评估（届时优先复用 JSON 解析而不是镜像类） | 现在就生成 SO（双 schema + 额外编辑器代码，收益要到 M5 才兑现） |

## 8. 联网 PVP 的预留：为什么"现在不做"也要现在定结构

阶段一交付的是 PVE，但阶段二要接的是**服务端权威状态同步**。它不需要"逻辑层零浮点"这种苛刻约束（这是此前帧同步方案的要求，已撤销），但它对代码结构有三条**不可事后打补丁**的要求：

```
状态同步能低成本落地的前提
  规则代码与 Unity 解耦 + 状态可序列化可裁剪可增量 + 操作统一走命令
        ↓
  服务器进程直接复用同一份规则代码（规则只有一处实现）
        ↓
  服务器按玩家视角裁剪状态 → 客户端只收到自己有权看到的内容
        ↓
  客户端只渲染、不结算 → 反作弊为中—高，手牌天然不泄露
```

### 8.1 阶段一必须做对的六件事（否则阶段二要重写内核）

| # | 现在必须做 | 如果做错的后果 |
| --- | --- | --- |
| 1 | 规则三层零 `UnityEngine` 依赖，只用 BCL | 服务器无法复用同一份代码，只能复制一份规则，从此长期双份维护 |
| 2 | 日志 / 时间 / 随机通过抽象注入，不直接调 Unity API | 服务器进程编译不过或行为不一致 |
| 3 | 所有玩家与 AI 操作走可序列化的 `GameCommand` | 没有可上行的"意图"，命令校验无从谈起 |
| 4 | `MatchState` 可序列化、可计算差异（增量） | 无法下发状态、无法重连、无法做视野裁剪 |
| 5 | 状态变更统一产出 `GameEvent` | 表现层与状态下发各写一套，事件顺序与结算不一致 |
| 6 | 网络与服务器代码独立成程序集，接口定义在 Application | PVE 被迫依赖网络层，无法单独出包与测试 |

### 8.2 由此产生的两条新约束（已写入 03 规范）

1. **`Card.Core` / `Card.Domain` / `Card.Application` 只允许依赖 BCL**（`System.*`）。Unity 特有的日志、时间、序列化、随机都必须换成自建抽象，由外层注入实现。表现层不受此限。
2. **依赖倒置。** `Card.Network` 与 `Card.Presentation` 互不引用：表现层需要网络能力时通过 `Card.Application` 中的接口（`IRoomService`、`IMatchSession`），由 Bootstrap 装配具体实现。

### 8.3 明确撤销的旧约束

此前版本曾把"逻辑层零浮点、零系统时间、固定遍历顺序、跨平台状态哈希一致"列为铁律（为帧同步服务）。**改为状态同步后这些全部撤销**：

- 规则层可以使用浮点数（仍**建议**优先整数，理由是便于测试与显示一致，属 P3 建议而非铁律）。
- 规则层不强制要求不依赖时间，但仍建议通过 `IClock` 抽象取时间，便于测试。
- 不再需要状态哈希校验，改为"版本号 + 快照 / 增量"。
- 随机数仍要求可注入种子，理由变为**测试可复现与服务端随机源**，不再是"双端逐位一致"。

### 8.4 三种部署拓扑（权威跑在哪里）

| 拓扑 | 权威宿主 | 适合 | 反作弊 | 本阶段 |
| --- | --- | --- | --- | --- |
| `LocalHost` | 客户端进程内（PVE / 离线） | 单机 PVE、教程、AI 对局 | 不涉及 | ✅ 已有 |
| `PeerHost` | **其中一个玩家客户端**（房主模式） | **本机双开验证**、局域网、朋友间对战 | 无（房主即对手） | ✅ **本阶段实现** |
| `DedicatedHost` | Unity 工程外的 `Card.Server` 进程 | 正式 PVP、竞技向 | 中—高 | ⬜ 只留接口 |

> 三者共用同一份 `MatchHost` 与规则代码，切换是配置级改动。
> **本阶段范围**：在一台 PC 上用两个进程（编辑器 + 构建，或两个构建）跑通 `PeerHost`，传输用 BCL TCP，**不需要匹配服务 / NAT 穿透 / 中继 / 反作弊**。
> 将来要做公网对战时，才需要补信令、中继与专用服务器（详见 [05 第 15 节](./05-联网对战_状态同步_设计文档.md)）。

> 结论：**PVP 是拓展功能，但"内核与 Unity 解耦 + 状态可序列化"是阶段一的基础功能。** 这一版方案比帧同步方案的阶段一成本明显更低；服务器成本也不再是硬前提——可以先用房主模式跑通，再按需上专用服务器。
